# Task-155: 저장소 접근은 application이 맡고 domain은 전달받은 사실로 판단한다

## Background

현재 도메인 저장소 계약은 `domain/repository`에 있고, `LabelNamePolicy`는 저장소를 직접 조회한다. 반면 `FriendshipBroker`는 application이 조회한 기존 친구 관계·요청의 존재 여부를 전달받는다. Label 멤버 추가·교체는 application에서 친구 관계를 잠금 조회하고 자격까지 판단한다. 이름 생성은 이름 정책을 거치지만 변경은 저장소를 직접 호출한다.

## Objective

저장소 계약을 `application/port/out`에 두고, application이 조회·잠금·저장을 조율하며 도메인 모델과 서비스는 전달받은 사실로 업무 규칙을 판단하도록 책임을 일관되게 정리한다. Label 이름 생성·변경과 멤버 추가·교체의 규칙도 이 경계를 따르게 한다.

## Decision

- 도메인의 저장소 계약을 application 출력 포트로 옮기되, domain이 이동한 포트를 참조하게 만들지 않는다. 도메인 모델과 서비스는 저장소를 직접 조회하거나 저장하지 않는다.
- application은 필요한 사실을 확보하고 domain은 그 사실의 업무적 의미를 판단한다. 허용 여부를 application이 미리 판단해 전달하지 않는다.
- Label 이름 고유성에는 같은 소유자 내 이름 중복 여부를 전달한다. 이름 변경 시 자기 자신을 중복으로 판정하지 않아야 한다.
- Label 멤버 자격에는 요청한 멤버 ID들과 해당 owner의 실제 친구 ID들을 전달한다. 단건 추가와 전체 교체에서 같은 도메인 판단을 사용하며, 친구가 아닌 대상들을 식별할 수 있어야 한다. 모든 입력을 boolean으로 축약하지 않는다.
- FriendshipBroker의 기존 친구 관계·요청 존재 여부를 외부에서 전달받는 방향을 유지한다.
- 도메인 서비스는 업무 행위나 판단을 구체적으로 드러내는 이름을 사용한다. 역할만을 기준으로 domain에 model/service 하위 패키지를 도입하지 않는다.
- 기존 잠금 순서, 트랜잭션 경계, DB 제약으로 보장하는 동시성 안전성을 보존한다. 일반 존재 조회나 boolean 전달만으로 동시성 보장이 대체된다고 간주하지 않는다.
- ARCHITECTURE.md의 도메인 저장소, 도메인 서비스, 출력 포트, 애플리케이션 서비스, 출력 어댑터와 의존성 설명은 해당 구현 변경과 같은 커밋 단위에서 갱신한다. 미구현 구조를 먼저 정본에 반영하지 않는다.

## Out of Scope

- HTTP 오류 매핑 분리(task-156).
- 업무 규칙, 외부 API 계약, 저장 기술의 변경.

## Acceptance Criteria

- domain에 저장소 계약이 남지 않고, 도메인 모델·서비스가 application 출력 포트나 영속성 어댑터에 의존하지 않는다.
- 도메인의 판단을 저장소 없이 전달한 사실만으로 검증할 수 있다.
- Label 생성·변경 모두 소유자별 이름 고유성을 적용하며, 자신의 기존 이름으로 변경하는 경우와 타 Label 이름과 충돌하는 경우를 구별한다.
- Label 단건 추가·전체 교체 모두 친구 자격을 도메인에서 판단한다. 빈 교체 목록과 비친구가 섞인 목록의 기존 동작을 유지한다.
- 친구 요청·관계 생성 조건과 기존 API 오류 계약을 유지한다.
- 동시 친구 해제와 Label 멤버 추가·교체에서 비친구 멤버십이 남지 않는지 관련 동시성 테스트로 확인한다.
- 영향받은 모듈의 컴파일과 관련 테스트가 통과하고, ARCHITECTURE.md가 실제 책임 경계와 일치한다.
