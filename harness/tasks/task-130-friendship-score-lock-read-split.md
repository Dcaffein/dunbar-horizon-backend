# Task-130: 점수 갱신이 잠금 쿼리와 읽기 쿼리를 나누고 계산을 도메인으로 되돌린다

## Background

관심도·친밀도를 갱신하는 저장소 쿼리 네 개(`incrementInterestScore`, `incrementMutualInterestScore`, `incrementMutualInterestScoresBatch`, `applyDecay`)는 한 쿼리 안에서 더미 속성으로 관계를 잠근 뒤 점수를 읽고 계산해 쓴다. block 포맷 DB에서 이 패턴이 동시 갱신을 오류 없이 잃는다.

2026-11-09 Neo4j Enterprise 2026.10.1에서 관계 20개에 200건/초로 5초(1,000건)를 넣어 경합시킨 결과다.

| 경로 | block | aligned |
| --- | --- | --- |
| 운영 원자적 쿼리 | 42~80건 유실 | 0건 |
| 같은 트랜잭션에서 잠금 쿼리를 먼저 실행하고 다음 쿼리에서 읽어 씀 | 0건 | 미측정 |
| 잠금 없이 `SET r.x = r.x + delta` 한 문장 증분 | 45~55건 유실 | 미측정 |
| 잠금 뒤 같은 쿼리에서 인덱스로 관계를 다시 찾아 읽음 | 43~52건 유실 | 미측정 |
| `apoc.lock.rels`로 잠그고 같은 쿼리에서 반환 | 23~42건 유실 | 미측정 |
| `apoc.lock.rels` 쿼리를 따로 실행한 뒤 읽음 | 0건 | 미측정 |

실행 계획은 잠금 다음에 읽도록 되어 있다. 원인은 확정하지 못했다. 확인된 범위는 "같은 쿼리 안의 읽기는 잠금 대기 전의 값이고, 다음 쿼리부터 최신 값"이라는 것이다. 공식 문서가 안전하다고 안내하는 더미 속성 잠금과 `SET n.prop = n.prop + 1`이 모두 block에서 깨졌다.

운영 Aura의 저장 포맷은 사용자가 확인 중이다. 테스트컨테이너는 `neo4j:5.24` Community라 block 포맷을 만들 수 없어 기존 동시성 테스트(`FriendshipScoreConcurrentWriteTest`)가 이 문제를 잡지 못한다.

비용도 함께 쟀다. 사용자 1만 명, `FRIENDS_WITH` 107만 개인 block DB에서 모임 30개(5명 12개, 8명 12개, 22명 6개, 1,842쌍)가 한 번에 끝나는 스윕을 동시 처리 8로 돌렸다.

| 경로 | 스윕 전체 | 22명 모임 하나의 쿼리 수 |
| --- | --- | --- |
| 잠금 쿼리 → Cypher 갱신 쿼리 | 약 100ms | 2 |
| 잠금 쿼리 → 일괄 로드 → 도메인 계산 → 일괄 쓰기 | 약 130ms | 3 |
| 같은 트랜잭션에서 쌍마다 잠금 → 로드 → 도메인 계산 → 쓰기 | 약 1.7s | 693 |

계산 위치만 다른 두 경로는 비용이 비슷하고, 쿼리 수만 다른 두 경로는 15배 차이가 났다. 단건 상호작용도 잠금 → `findById` → 도메인 계산 → 쓰기로 500건/초를 처리했다. 측정 코드와 결과는 `exp/perf-interaction-score-rebench` 브랜치와 `Neo4jOptimizeTest/profiling/results/interaction-rebench`, `flag-sweep`에 있다.

## Objective

점수를 바꾸는 모든 경로가 같은 트랜잭션에서 잠금 쿼리를 먼저 끝낸 뒤, 다음 쿼리부터 점수를 읽는다. 단건 상호작용과 모임 종료 배치는 잠금 → 로드 → 도메인 메서드로 계산 → 쓰기로 바뀌어, 친밀도 계산 규칙이 도메인 한 곳에 남는다. 감쇄는 Cypher로 계산하되 잠금과 갱신을 다른 쿼리로 나눈다. 테스트는 Enterprise 테스트컨테이너의 block 포맷 DB에서 돌아, 수정 전 쿼리의 유실을 재현하고 수정 후 유실이 없음을 확인한다.

## Decision

### 잠금과 읽기는 다른 쿼리로 나눈다

잠금 수단과 상관없이 같은 쿼리 안의 읽기는 낡았고, 다음 쿼리에서 읽으면 최신이었다. 잠금은 트랜잭션 끝까지 유지되므로, 잠금 쿼리를 먼저 끝내면 이후 쿼리들은 다른 트랜잭션의 개입 없이 최신 값을 읽고 쓴다. 잠금 쿼리는 값을 반환하지 않는다.

### 잠금은 더미 속성 쓰기를 유지한다

`apoc.lock.rels`는 기각한다. 쿼리를 나누면 두 방식의 결과가 같았고(유실 0), 바꾸면 쓰기 경로가 APOC에 의존하게 된다. 잠금은 관계 단위로 걸리므로 더미 속성 하나로 그 관계의 모든 속성 변경이 막힌다. 일반 조회는 잠금을 기다리지 않는다.

### 계산은 도메인에서 하고, 배치는 한꺼번에 처리한다

비용을 정한 것은 계산 위치가 아니라 쿼리 수였다. 그래서 친밀도 공식을 Cypher에 복제할 이유가 없다. 배치는 대상 관계 전체를 한 번에 잠그고, 한 번에 로드하고, 한 번에 쓴다.

쌍마다 처리하는 방식은 기각한다. 쿼리 수가 쌍 수에 비례해 15배 느렸고, 잠금을 오래 쥐어 겹치는 모임과 단건 상호작용이 그만큼 기다린다. 예전처럼 쌍마다 이벤트를 발행하는 구조로도 돌아가지 않는다.

### 잠금 순서는 id 오름차순을 유지한다

여러 관계를 잠그는 쿼리는 friendshipId로 정렬해 잠근다. 교착을 막는 기존 규약이다.

### 감쇄는 Cypher를 유지한다

감쇄 대상은 관계 전체라 애플리케이션으로 불러오면 무겁다. 계산은 Cypher에 두고 잠금 쿼리와 갱신 쿼리만 나눈다. 감쇄 스케줄러는 지금 꺼져 있다.

### 테스트는 Enterprise 테스트컨테이너의 block 포맷에서 돈다

`TestContainerConfig`의 Neo4j 이미지를 Enterprise로 바꾸고 block 포맷을 명시한다. CI는 `./gradlew build`로 테스트를 돌리므로 같은 설정이 그대로 적용된다. Enterprise 이미지는 라이선스 동의가 필요하며, 동의 여부는 사용자가 확인한다. 버전은 운영 Aura에 가깝게 고르고 PLAN에서 정한다.

## Out of Scope

- 운영 Aura의 저장 포맷 확인과, 유실이 있었다면 그 점수의 보정
- 친구 관계 개인 설정 변경(`updateUserRelationshipFields`). 받은 값을 그대로 써서 낡은 값의 영향이 없다
- 친구 요청 상태 변경처럼 애플리케이션에서 읽고 확인한 뒤 다른 쿼리로 바꾸는 흐름의 경합
- 이벤트 구조(`BatchMutualInteractionEvent`)와 비동기 풀 설정
- 측정용 벤치마크 코드의 병합

## Acceptance Criteria

- block 포맷 테스트컨테이너에서 같은 관계에 동시 갱신을 몰아넣는 테스트가, 수정 전 쿼리로는 유실을 재현해 실패하고 수정 후에는 통과한다. 단건 상호, 단건 단방향, 배치 경로를 모두 다룬다.
- 감쇄도 같은 조건에서 점수가 어긋나지 않는다.
- 점수를 바꾸는 모든 경로에서 잠금 쿼리가 점수를 읽는 쿼리보다 먼저, 별도로 실행된다.
- 단건과 배치의 계산 결과가 도메인 메서드 결과와 같고, 친밀도 공식이 감쇄 쿼리를 제외한 Cypher에 남아 있지 않다.
- 배치는 쌍 수와 관계없이 쿼리 수가 일정하다.
- 여러 관계를 잠그는 쿼리는 friendshipId 오름차순으로 잠근다.
- 기존 소셜·플래그 테스트가 Enterprise 테스트컨테이너에서 모두 통과한다.
