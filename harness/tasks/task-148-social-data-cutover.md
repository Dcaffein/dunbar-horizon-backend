# Task-148: Social 데이터를 이관하고 Neo4j 의존성을 제거한다

## Background

친구 요청 수락, 친구 끊기와 라벨 정리, 관계망 조회가 공통 데이터를 사용한다. 각 저장소를 따로 전환하면 쓰기 결과와 조회 기준이 다른 DB에 놓일 수 있다.

## Objective

계정 원본 조회, 친구 관계·요청과 라벨의 저장, 관계망·추천·연결 중개인의 MySQL 경로가 준비되면 기존 Neo4j Social 데이터를 이관하고 검증한다. Social의 읽기·쓰기를 MySQL로 함께 전환하고 애플리케이션과 통합 테스트에서 Neo4j 의존성을 제거한다.

## Decision

- 서비스가 참조하는 저장소는 한 번에 전환한다. 이관에 사용한 원본 시점과 읽기·쓰기 전환 사이에 생긴 변경이 누락되지 않게 한다.
- 친구 관계의 생성일과 양방향 설정·점수·시각, 친구 요청의 방향·상태·생성 시각, 라벨의 ID·이름·소유자와 멤버십을 이관한다. 사용자는 MySQL 계정 ID에 매핑하고 기존 아카이브는 보존한다.
- 중복 친구 요청, 연결할 계정이 없는 데이터, 친구가 아닌 라벨 멤버십 등 충돌을 검출하고 처리 결과를 확인할 수 있어야 한다. 행 개수와 함께 키·속성·연결의 일치 여부를 검증한다.
- 계정 원본을 사용하면 필요 없어지는 Social 동기화, Lazy Sync, 전용 Outbox 경로를 정리한다. Neo4j와 APOC를 사용하는 애플리케이션 설정, 의존성, 테스트 구성을 제거한다.
- MySQL의 도메인 모델은 사용자 ID를 보유하고, 조회 결과에서 표시 정보가 필요할 때 Social의 읽기 SQL이 `users`에서 가져온다. 두 저장소가 공존하는 동안 사용한 `UserReference` 인터페이스를 제거한다.

## Acceptance Criteria

- 샘플 Neo4j 데이터로 이관을 실행하고, 정상 데이터와 충돌 데이터가 각각 어떻게 처리됐는지 결과로 확인할 수 있다. 같은 입력으로 재실행해도 관계와 라벨 멤버십이 중복되지 않는다.
- 이관 데이터로 친구 요청 수락, 친밀도 갱신, 친구 끊기와 라벨 정리, 관계망·추천·연결 중개인 조회가 MySQL을 통해 동작한다.
- Neo4j 연결 없이 앱이 기동하고 관련 통합 테스트가 통과한다. 프로필·계정 상태 변경에 Social 전용 복제 작업이 필요하지 않다.
