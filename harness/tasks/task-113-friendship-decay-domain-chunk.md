# Task-113: 친구 관계 감쇄의 도메인 이관 및 chunk 처리

## 목적

친구 관계 감쇄 쿼리에 포함된 도메인 계산을 도메인으로 옮기고, 하루 한 번 실행하는 스케줄러에서 대상을 chunk로 나누어 처리한다.

현재 `InteractionScoreFlushService`는 도메인 메서드로 관심도와 친밀도를 계산한 뒤 일괄 저장하지만, `FriendshipDecayService`가 호출하는 저장소 쿼리는 감쇄와 친밀도 계산을 직접 수행한다. 정규화 상수 `50.0`과 친밀도 공식이 도메인과 쿼리에 중복되어 규칙 변경 시 결과가 달라질 수 있다. 계산 규칙을 도메인에 모으면서 전체 대상의 일괄 로딩과 장시간 트랜잭션을 피하는 것이 목적이다.

## 결정사항 및 제약

- 감쇄와 친밀도 재계산은 도메인이 책임지고, 저장소는 대상 조회와 계산 결과 저장을 담당한다.
- 하루 한 번의 스케줄 실행에서 여러 chunk를 처리하며, 메모리 사용량과 트랜잭션 범위를 제한한다.
- 기존 감쇄율, 교류 유예 기간, 관심도 하한 및 친밀도 공식의 의미를 유지한다.
- 감쇄는 교류가 아니므로 `lastInteractedAt`을 갱신하지 않는다. 기존 `adjustInterestScore()`는 이 시각을 갱신하므로 그대로 재사용할 수 없다.
- 감쇄 대상은 방향별로 판단하되, 친밀도는 친구 관계 양쪽의 최종 관심도로 계산한다.
- 작업 전체에서 감쇄 대상 판정의 기준 시각을 일관되게 사용한다.
- 구체적인 변경 파일, chunk 크기, 조회·저장 방식과 동시성 제어 방식은 작업 의뢰 후 코드 탐색 및 PLAN 승인 단계에서 확정한다.

## 반드시 다룰 경계 조건

- 처리 도중 점수가 하한에 도달해 대상 목록에서 빠져도 다음 대상이 누락되지 않아야 한다. ID 기반 순회 등을 검토한다.
- 한쪽만 감쇄 대상인 관계에서도 반대쪽 관심도를 유지하고 친밀도를 올바르게 재계산해야 한다.
- 중간 실패 후 재실행하거나 스케줄이 중복 실행되어도 같은 처리일의 감쇄가 중복 적용되지 않아야 한다. 처리일의 시간대와 재시작 기준을 명확히 한다.
- Flush와 감쇄가 같은 관계를 동시에 수정할 때 관심도 증가분이나 감쇄 결과가 유실되지 않아야 한다. 두 쓰기 경로를 함께 검토한다.
- chunk 사이 또는 조회·저장 사이에 친구 관계가 삭제되거나 교류가 발생하는 경우를 다룬다.
- 전체 작업을 하나의 트랜잭션으로 묶지 않고, 실패한 chunk의 롤백과 이미 완료된 chunk의 재처리 안전성을 고려한다.

## 범위 제외

- 친밀도 공식 및 감쇄 정책 수치의 제품적 변경
- API 계약 변경
- 친구 관계 아카이브 정책의 재설계
- 상호작용 수집·Flush 파이프라인 전반의 재설계. 단, 감쇄와의 동시 수정 안전성 확보에 필요한 변경은 검토한다.
