# Task Spec Guide

"무엇을, 어떻게" 구현할지는 에이전트가 코드베이스를 분석하여 PLAN.md에서 도출합니다.
이 명세서(Task Spec)에는 에이전트가 코드만 보고는 알 수 없는 맥락과 확정된 제약만 작성합니다.
그래서 변경할 파일 목록은 여기에 적지 않습니다.

## 섹션

아래 구조를 그대로 따릅니다. 섹션을 늘리거나 이름을 바꾸지 않습니다.

| 섹션 | 필수 | 설명 |
|------|------|------|
| Background | — | 왜 이 작업이 필요한가. 확인한 사실만 쓰고 추측은 추측이라고 밝힌다. 증상이 있으면 재현 조건과 영향 범위를 함께 적는다 |
| Objective | ✓ | 이 작업이 끝났을 때 무엇이 달라지는가. 한 문단으로 쓴다 |
| Decision | — | 인간이 사전에 확정한, 변경하면 안 되는 방향과 그 근거. 기각한 선택지가 있으면 기각 이유까지 남긴다 |
| Out of Scope | — | 이 작업에서 건드리지 않을 것. 인접해서 눈에 띄지만 별건인 것 |
| Acceptance Criteria | ✓ | 무엇을 확인하면 끝인지 검증 가능한 문장으로 쓴다. 버그 수정이면 회귀 테스트가 수정 전 동작에서 실패하는지 확인하는 항목을 넣는다 |

근거를 Background로 떼어놓지 않습니다. 어떤 사실이 특정 결정만을 위한 것이면 그 결정 아래에 둡니다.
작업 결과는 이 문서에 쓰지 않습니다. 최종 결정과 동작 변경은 커밋 메시지가 정본이고,
완료 처리는 `WORKFLOW.md` 6단계를 따릅니다.
