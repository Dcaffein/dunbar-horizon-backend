# Task-151: FriendRequest 애그리거트와 저장 방식을 다시 세운다

## Background

Social을 MySQL로 이관한 뒤에도 FriendRequest 주변에는 Neo4j 시절의 구조가 남아 있다.

- 요청이 문자열 ID(`"작은ID_큰ID"`)를 만들어 들고 있다. Neo4j에 복합 키가 없어 쌍의 유일성과 조회를 문자열 하나로 흉내 낸 것이다. MySQL로 옮긴 뒤에는 요청자·수신자 두 값의 사본이다.
- 테이블 PK는 `(low_user_id, high_user_id)`이고 방향은 별도 열에 있다. low/high는 순서 없는 쌍의 유일성을 걸기 위한 장치일 뿐이다.
- 전송은 사전 확인 뒤 요청을 넣고 관계를 `FOR UPDATE`로 다시 확인한다. 수락은 요청 행과 관계를 각각 `FOR UPDATE`로 잠근다.
- 숨긴 요청은 만든 지 1개월 뒤 스케줄러가 지운다. 숨긴 요청은 요청자의 보낸 목록에 보이지 않고 요청자가 취소할 수도 없다.
- 서비스는 요청자용·수신자용 입력 포트 둘을 구현하는 명령 서비스, 조회 서비스, 정리 서비스로 나뉘어 있다.

## Objective

FriendRequest가 요청자·수신자로 식별되는 JPA 애그리거트가 되고, 상태 전이 규칙은 State가 소유한다. 전송·수락·취소의 동시성은 잠금 없이 DB 제약과 행 수 확인으로 지켜진다. 숨김은 거절 대신의 완곡한 거절로 영원히 남고, 요청자는 숨겨진 요청을 대기 중인 요청으로 보고 취소할 수 있다. 요청의 유스케이스는 서비스 하나에 모인다.

## Decision

- `ACCEPTED`는 상태로 유지한다. State 안에서 전이만 하는 종결 상태다. 수락하면 애플리케이션이 같은 트랜잭션에서 친구 관계를 만들고 요청을 바로 지운다. 기각한 대안은 `ACCEPTED`를 저장해 두고 스케줄러가 지우는 방식이다. 친구를 끊고 다시 요청하면 남은 행과 키가 겹치고, 남긴 행을 읽는 곳이 없다.
- 요청은 문자열 ID 없이 요청자·수신자로 식별한다. `id` 필드와 `generateId`를 없앤다. 응답의 `id`는 경계에서 두 ID로 지금 형식(`"작은ID_큰ID"`)을 만들어 API를 유지한다.
- 숨김은 영원히 남는다. 숨김 정리 스케줄러와 서비스, 보관 기간을 없앤다. 요청자는 `PENDING`과 `HIDDEN` 모두에서 취소할 수 있다. 숨김은 그 요청을 치워 두는 것이고, 보내고 취소하기를 반복하는 남용은 차단이나 전송 제한 같은 별도 기능이 막을 일이다.
- 요청자의 보낸 목록에는 숨겨진 요청도 `PENDING`으로 보인다. 숨겨졌다는 사실을 요청자에게 알리지 않는다.
- FriendRequest 저장은 JPA로 한다. 경로가 모두 애그리거트 하나를 읽고 도메인이 검증해 저장하는 방식이라 JDBC가 필요 없다. 도메인 클래스를 그대로 엔티티로 쓰고, 도메인에는 `jakarta.persistence` 표준 어노테이션만 둔다. task-152 뒤로 `friendships`도 애그리거트 경로는 JPA라, 수락은 한 트랜잭션에서 두 테이블을 모두 JPA로 다룬다.
- 테이블 PK를 `(requester_id, receiver_id)`로 바꾸고, 순서 없는 쌍의 유일성은 `(LEAST, GREATEST)` 함수 유일 인덱스로 건다. low/high 열과 쌍 CHECK를 없앤다. 운영 MySQL은 8.4.11이라 함수 인덱스를 쓸 수 있다.
- 동시성은 잠금 없이 다룬다.
  - 동시 전송: 먼저 들어간 요청만 남고 늦은 쪽은 쌍 유일성 인덱스에 걸려 "이미 요청이 있음"으로 끝난다.
  - 수락·취소·숨김의 경합: 먼저 처리된 쪽이 이긴다. 늦은 쪽은 지우거나 고칠 행의 수가 맞지 않아 실패하고 롤백된다. 수락이 지면 같은 트랜잭션에서 만든 관계도 함께 되돌아간다. 진 쪽은 409를 받는다.
  - 근거: 같은 요청을 동시에 처리하는 사람은 요청자와 수신자 둘뿐이고, 진 쪽은 다시 보면 된다. 읽기와 쓰기가 한 트랜잭션 안에서 끝나므로 버전을 실어 보낼 필요도 없다.
- 전송은 이 쌍의 요청이 있는지, 친구인지를 잠금 없이 조회해 Broker에 사실로 넘긴다. Broker는 규칙("이미 친구면 요청할 수 없다", "요청이 있으면 새 요청을 할 수 없다")을 판단한다.
- "이미 친구면 요청할 수 없다"는 요청과 관계 두 테이블에 걸쳐 있어 DB 제약으로 막을 수 없다. A→B 전송의 확인과 저장 사이에 B→A 요청이 생기고 A가 그것을 수락까지 커밋하면 친구 사이에 대기 요청이 남는다. 이 구멍은 막지 않는다. 한 사용자가 보내기와 수락을 동시에 해야 생기는 경우라 사실상 일어나지 않고, 일어나도 관계 무결성은 관계 PK가 지킨다. 남은 요청은 수락하면 409로 끝나고, 요청자는 취소, 수신자는 숨길 수 있다. 기각한 대안은 요청을 저장한 직후 친구 여부를 다시 조회하는 방식이다. 기본 격리 수준(REPEATABLE READ)의 스냅샷으로는 그사이 커밋된 수락이 보이지 않아 이 메서드만 READ COMMITTED가 필요하고, 그 이유를 설명하고 지키는 비용이 막는 경우에 비해 크다. 요청과 관계를 한 테이블로 합치는 구조 변경과, 전송과 수락이 같은 잠금을 잡는 방식도 기각한다.
- 요청의 유스케이스(목록, 전송, 취소, 상태 변경)는 `FriendRequestService` 하나와 입력 포트 `FriendRequestUseCase` 하나에 둔다. 쓰는 곳이 컨트롤러뿐이고 한 기능 안의 일이라 조회와 명령을 나눌 이유가 없다. 파라미터는 `(currentUserId, counterpartId)`로 맞춘다. `ARCHITECTURE.md`의 서비스 기준을 같은 판단으로 고친다.

## Out of Scope

- Friendship 저장의 JPA·JDBC 분리. task-152에서 다룬다.
- Label 모델과 저장 방식.
- 차단, 전송 횟수 제한 같은 남용 방어 기능.
- `ARCHITECTURE.md` §2 저장소 사용 전략 개정.

## Acceptance Criteria

- `FriendRequest`에 문자열 ID가 없고, 요청자·수신자로 식별된다. 응답의 `id` 형식은 바뀌지 않는다.
- 서로에게 동시에 보낸 요청은 한 건만 남는다. 수락과 취소가 동시에 오면 한쪽만 성공하고, 수락이 지면 관계도 생기지 않는다. 같은 요청을 두 번 수락하면 한 번만 성공한다. 진 쪽은 409를 받는다.
- 숨긴 요청은 자동으로 지워지지 않는다. 요청자는 숨겨진 요청을 보낸 목록에서 `PENDING`으로 보고 취소할 수 있다.
- 상대가 비활성이면 단건 처리는 "요청 없음", 목록에서는 보이지 않는다.
- 마이그레이션 뒤 기존 요청이 그대로 조회되고 처리된다.
- Social, Buzz, Flag 테스트가 통과한다.
