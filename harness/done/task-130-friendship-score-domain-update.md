# Task-130: 관심도·친밀도 갱신을 도메인 로직으로 되돌린다

## Background

관심도·친밀도 갱신은 지금 저장소 Cypher가 계산까지 맡는다. 단건 상호작용, 모임 종료 배치, 감쇄 쿼리가 각자 친밀도 공식을 갖고 있다. 이 구조는 "도메인 객체를 불러와 계산하고 저장하면 느리다"는 전제에서 나왔다.

그 전제를 현재 모델에서 다시 쟀다. 사용자 1만 명, `FRIENDS_WITH` 107만 개인 block DB에서 모임 30개(5명 12개, 8명 12개, 22명 6개, 1,842쌍)가 한 번에 끝나는 스윕을 동시 처리 8로 돌렸다.

| 경로 | 스윕 전체 | 22명 모임 하나의 쿼리 수 |
| --- | --- | --- |
| 잠금 → Cypher로 계산·갱신 | 약 100ms | 2 |
| 잠금 → 일괄 로드 → 도메인 계산 → 일괄 쓰기 | 약 130ms | 3 |
| (대조) 같은 트랜잭션에서 쌍마다 잠금 → 로드 → 도메인 계산 → 쓰기 | 약 1.7s | 693 |

마지막 행은 대안이 아니라 쿼리 수의 영향을 보려는 대조 측정이다. 계산 위치만 다른 두 경로는 비용이 비슷하고, 쿼리 수만 다른 두 경로는 15배 차이가 났다. 비용을 정하는 것은 계산 위치가 아니라 쿼리 수였다. 단건도 잠금 → `findById` → 도메인 계산 → 쓰기로 500건/초를 p50 5~6ms에 처리했다. 예전에 느렸던 원인은 SDN 매핑·저장, 낙관적 잠금 재시도, 쌍마다 쪼갠 이벤트였던 것으로 본다.

측정 중 정합성 문제도 드러났다. 지금 Cypher는 한 쿼리 안에서 더미 속성으로 관계를 잠근 뒤 점수를 읽는데, block 포맷 DB에서 이 패턴이 동시 갱신을 오류 없이 잃는다. Neo4j Enterprise 2026.10.1에서 관계 20개에 200건/초로 5초(1,000건)를 넣어 경합시킨 결과다.

| 경로 | block | aligned |
| --- | --- | --- |
| 운영 원자적 쿼리 | 42~80건 유실 | 0건 |
| 같은 트랜잭션에서 잠금 쿼리를 먼저 실행하고 다음 쿼리에서 읽어 씀 | 0건 | 미측정 |
| 잠금 없이 `SET r.x = r.x + delta` 한 문장 증분 | 45~55건 유실 | 미측정 |
| 잠금 뒤 같은 쿼리에서 인덱스로 관계를 다시 찾아 읽음 | 43~52건 유실 | 미측정 |

실행 계획은 잠금 다음에 읽도록 되어 있다. 원인은 구현 중에 실행 계획으로 좁혔고 "잠금과 읽기는 다른 쿼리로 나눈다" 항목에 적는다. 확인된 범위는 "같은 쿼리 안의 읽기는 잠금 대기 전의 값이고, 다음 쿼리부터 최신 값"이라는 것이다. 공식 문서가 안전하다고 안내하는 두 방법이 모두 block에서 깨졌다. 테스트컨테이너는 `neo4j:5.24` Community라 block 포맷을 만들 수 없어 기존 동시성 테스트가 이 문제를 잡지 못한다.

## Objective

단건 상호작용과 모임 종료 배치의 관심도·친밀도 갱신이 도메인 로직으로 돌아온다. 저장소는 관계를 잠그고, 불러오고, 도메인이 계산한 값을 쓰기만 하며, 친밀도 계산 규칙은 도메인 한 곳에 남는다. 이 과정에서 잠금 쿼리와 읽기 쿼리를 나눠 block 포맷에서도 갱신이 유실되지 않는다. 감쇄는 Cypher 계산을 유지하되 같은 방식으로 잠금과 갱신을 나눈다. 테스트는 Enterprise 테스트컨테이너의 block 포맷 DB에서 돈다.

## Decision

### 갱신 경로를 도메인 로직으로 되돌린다

비용을 정한 것은 계산 위치가 아니라 쿼리 수였다. 계산을 Cypher에 둘 이유가 없으므로 도메인 메서드로 계산하고, 저장소는 잠금, 로드, 쓰기만 맡는다.

- **단건:** 잠금 → `findById` → 도메인 계산 → 쓰기
- **모임 종료 배치:** 대상 관계 전체를 한 번에 잠금 → 한 번에 로드 → 쌍마다 도메인 계산 → 한 번에 쓰기. 쌍 수와 관계없이 쿼리 수가 일정하다.

Cypher로 계산하는 안(잠금과 갱신만 분리)은 기각한다. 비용은 비슷하지만 친밀도 공식이 Cypher 여러 곳에 복제된다.

쌍마다 이벤트를 발행하던 task-28 이전 구조로는 돌아가지 않는다. 비동기 작업과 커밋이 쌍 수만큼 생기고, 모임 단위로 함께 반영되거나 함께 실패하지 않는다. 이번에 측정하지는 않았다.

도메인 계산은 로드와 Java 계산만큼 잠금을 조금 더 오래 쥔다. 스윕 측정에서 배치 하나의 최대 시간 차이는 10~20ms였고, 감수한다.

### 감쇄는 Cypher 계산을 유지한다

감쇄 대상은 관계 전체라 애플리케이션으로 불러오면 무겁다. 감쇄만 Cypher에서 계산한다. 감쇄 스케줄러는 지금 꺼져 있다.

### 구현: 잠금과 읽기는 다른 쿼리로 나눈다

같은 쿼리 안의 읽기는 낡았고, 다음 쿼리에서 읽으면 최신이었다. 잠금은 트랜잭션 끝까지 유지되므로, 잠금 쿼리를 먼저 끝내면 이후 쿼리들은 다른 트랜잭션의 개입 없이 최신 값을 읽고 쓴다. 잠금 쿼리는 값을 반환하지 않는다. 감쇄도 잠금 쿼리와 갱신 쿼리를 나눈다.

**원인(실행 계획으로 좁힌 추정):** 테스트컨테이너(5.26 Enterprise, block)에서 옛 점수 쿼리를 PROFILE하면, 관계를 찾는 `Expand`부터 잠금 `SetProperty`, 점수를 읽는 `CacheProperties`까지 한 파이프라인으로 합쳐진다(Fused). 합쳐진 파이프라인은 관계를 처음 읽은 커서를 끝까지 쓰고, block 포맷은 관계 레코드와 속성을 한 블록에 담으므로 잠금 전에 읽은 점수가 잠금 뒤에도 쓰인다. aligned 포맷은 속성을 별도 저장소에서 따로 읽어 그 시점이 잠금 뒤라 유실이 없었던 것으로 본다. 다음 쿼리는 새 커서로 읽으므로 분리하면 계획 모양과 관계없이 최신 값을 읽는다. Neo4j 내부 코드로 확인한 것은 아니다.

**정렬로 한 쿼리를 유지하는 안은 기각한다.** 관계를 찾은 뒤 잠그기 전에 `WITH r ORDER BY r.id`를 끼우면 `Sort`가 파이프라인을 끊어 잠금 뒤 연산자가 관계를 새로 읽는다. 같은 하네스(관계 6개에 600건 동시 증분)에서 옛 점수 쿼리는 344~370건을 잃었고, 정렬만 끼우면 0건이었다. 지금 감쇄 쿼리가 유실 없이 돌았던 것도 이 정렬 덕분이고, 감쇄 모양에서 정렬만 빼면 264~282건을 잃었다. 잠금 전 `WHERE`나 관계를 유저에서 찾아가는 방식은 유실과 무관했다. 그래도 정렬에 맡기지 않는다. 파이프라인을 끊을지는 플래너와 런타임이 정하고, 결과가 한 행이거나 인덱스가 순서를 보장하면 정렬이 빠질 수 있으며, 운영 Aura(5.27-aura, 인덱스 있음)의 계획은 확인하지 않았다. 쿼리를 하나 줄여 얻는 것은 왕복 한 번뿐이다.

### 구현: 잠금 전에는 대상 관계를 읽지 않는다

같은 트랜잭션에서 잠금 쿼리보다 먼저 대상 관계를 읽으면, 그 값으로 계산해 같은 lost update가 난다. 잠금 쿼리가 트랜잭션의 첫 쿼리가 되도록 한다.

### 구현: 잠금은 더미 속성 쓰기를 유지한다

Neo4j는 쓰기 시점에 관계 단위로 잠그므로, 더미 속성 하나로 그 관계의 모든 속성 변경이 막힌다. 일반 조회는 잠금을 기다리지 않는다.

### 구현: 잠금 순서는 id 오름차순을 유지한다

여러 관계를 잠그는 쿼리는 friendshipId로 정렬해 잠근다. 교착을 막는 기존 규약이다. 이 정렬은 교착 방지용이고 낡은 읽기를 막는 수단이 아니다. 낡은 읽기는 쿼리 분리로 막는다.

### 테스트는 Enterprise 테스트컨테이너의 block 포맷에서 돈다

`TestContainerConfig`의 Neo4j 이미지를 Enterprise로 바꾸고 block 포맷을 명시한다. CI는 `./gradlew build`로 테스트를 돌리므로 같은 설정이 그대로 적용된다. Enterprise 이미지는 라이선스 동의가 필요하며, 동의 여부는 사용자가 확인한다. 버전은 운영 Aura(5.27-aura, Docker 이미지 없음)에 가장 가까운 LTS인 `neo4j:5.26-enterprise`로 정했고, 이 버전에서 유실이 재현됐다. 동의는 `container-license-acceptance.txt`로 확인한다.

### 동등성 비교 테스트는 지우고, 동작 테스트는 새 경로로 옮긴다

Cypher 계산이 도메인과 같은지 비교하던 테스트는 비교할 Cypher 계산이 사라지므로 지운다. 회수 시 0에서 멈추는 규칙은 도메인 테스트가 지킨다. 감쇄 테스트는 그대로 둔다. 동시 갱신 테스트와, 높은 id 쪽 점수와 교류 시각만 바뀌는지 보는 쪽 구분 테스트는 새 경로 기준으로 유지한다.

## Out of Scope

- 친구 관계 개인 설정 변경(`updateUserRelationshipFields`). 받은 값을 그대로 써서 낡은 값의 영향이 없다
- 친구 요청 상태 변경처럼 애플리케이션에서 읽고 확인한 뒤 다른 쿼리로 바꾸는 흐름의 경합
- 이벤트 구조(`BatchMutualInteractionEvent`)와 비동기 풀 설정

## Acceptance Criteria

- 단건과 배치의 관심도·친밀도 계산이 도메인 메서드로 이뤄지고, 친밀도 공식이 감쇄 쿼리를 제외한 Cypher에 남아 있지 않다.
- 배치는 쌍 수와 관계없이 쿼리 수가 일정하다.
- block 포맷 테스트컨테이너에서 같은 관계에 동시 갱신을 몰아넣는 테스트가, 수정 전 쿼리로는 유실을 재현해 실패하고 수정 후에는 통과한다. 단건 상호, 단건 단방향, 배치 경로를 모두 다룬다.
- 감쇄도 같은 조건에서 점수가 어긋나지 않는다.
- 점수를 바꾸는 모든 경로에서 잠금 쿼리가 트랜잭션의 첫 쿼리로, 점수를 읽는 쿼리보다 먼저 별도로 실행된다.
- 여러 관계를 잠그는 쿼리는 friendshipId 오름차순으로 잠근다.
- 기존 소셜·플래그 테스트가 Enterprise 테스트컨테이너에서 모두 통과한다.
