# Task-131: Flag 도메인 서비스의 책임 경계를 정리한다

## Background

task-129는 자동 만료 면제가 후기·앵콜의 실제 존재와 어긋나 사용자 데이터를 삭제하는 경합을 막았다. 이를 위해 FlagMemorialManager, FlagEncoreManager, FlagDeletionManager를 만들고 잠금 조회 → 변경·저장 → 면제 재계산을 한 메서드로 묶었다. 이후 커밋 7a5b050에서 MemorialFactory와 EncoreFactory의 검증·생성도 각 Manager로 합쳤다.

이 세 Manager가 추가된 직접적인 이유는 독립적인 도메인 정책이 아니라 잠금과 저장의 실행 순서였다. Manager를 호출하기 전 일반 조회를 하면 읽기 시점이 고정될 수 있다는 전제도 애플리케이션에 남아 있어, 순서 책임이 완전히 캡슐화된 것은 아니다. 단일 유스케이스의 절차와 여러 경로가 공유하는 도메인 연산을 같은 Manager 이름으로 묶으면서 책임이 불명확해졌다.

## Objective

Flag의 도메인 서비스는 FlagParticipationManager와 FlagExpiryExemptionUpdater만 유지한다. 나머지 네 Manager를 해체하고 모델이 판단할 수 있는 생성·권한 규칙은 모델에, 각 유스케이스의 조회·잠금·저장 순서는 애플리케이션에 배치한다. task-129의 동시성 보장과 기존 제품 규칙은 유지하고, 해체·유지 이유 및 책임 배치 기준을 harness 아키텍처 문서에 남긴다.

## Decision

### 단일 유스케이스의 실행 순서를 묶은 세 Manager를 해체한다

- FlagMemorialManager: 후기 생성·삭제의 잠금, 저장, 면제 재계산 순서는 애플리케이션이 조율한다. 후기 생성 시 필요한 Flag 상태·작성 자격은 Memorial이 전달받은 정보로 판단하고, 삭제 권한도 Memorial이 판단한다.
- FlagEncoreManager: 부모 잠금, 앵콜 저장, 부모 면제 재계산은 애플리케이션이 조율한다. 호스트·종료 상태·기존 앵콜 존재에 따른 생성 가능 여부는 Flag가 판단한다.
- FlagDeletionManager: 삭제 대상과 부모의 잠금·저장 순서는 애플리케이션이 조율한다. 호스트 권한, 자신의 면제 해제, 소프트 삭제와 부모 링크 제거는 Flag가 담당한다.

이 해체는 task-129의 잠금이나 동시성 요구를 폐기하는 결정이 아니다. 그 요구를 집행하는 위치를 바꾼다.

### FlagInvitationManager도 해체한다

모집 중인 Flag에만 초대 가능, 발신자는 호스트 또는 초대 권한이 있는 참여자, 호스트·기존 참여자·기존 초대에 대한 제한은 필요한 객체와 조회 사실을 받은 FlagInvitation의 생성 규칙으로 둔다. 수락자가 수신자인지 판단하는 규칙은 기존 FlagInvitation에 남긴다.

애플리케이션은 초대 조회 → 수신자 검증 → FlagParticipationManager 호출 → 참여자 저장 → 초대 삭제를 조율한다. 초대 권한 변경은 Flag와 해당 참여자를 준비하고 기존 Flag의 권한 변경 메서드를 호출한다. 이 작업들을 묶기 위한 대체 Manager는 만들지 않는다.

### FlagParticipationManager는 공통 참여 경로로 유지한다

직접 참여와 초대를 통한 참여가 Flag 잠금 → 중복 참여 확인 → 현재 참여자 수 조회 → Flag의 참여 판단을 공유한다. 이 경로를 각 애플리케이션에 복제하면 잠금 위치와 참여 규칙이 갈라질 수 있어 유지한다. 기존 조회·잠금과 탈퇴 처리 책임을 유지하고, 참여자 저장·삭제까지 가져오지는 않는다.

### FlagExpiryExemptionUpdater는 공통 면제 갱신으로 유지한다

후기 생성·삭제, 앵콜 생성·수동 삭제에서 같은 규칙인 '후기 존재 OR 삭제되지 않은 직계 앵콜 존재'를 적용한다. 관련 존재 여부 조회와 Flag 상태 변경을 이 서비스 한곳에 유지한다. 호출자가 잠근 Flag를 전달하며, 원천 변경의 저장·삭제 뒤 명시적으로 호출하고 Flag 저장은 애플리케이션이 수행한다. 이벤트를 통한 면제 동기화로 되돌리지 않는다.

### 모델이 판단할 수 있는 규칙에는 객체 또는 사실을 전달한다

- FlagMemorial은 생성 시 Flag와 작성자의 참여 여부를 받아 종료 상태·호스트/참여 자격·내용을 판단한다. Flag는 Memorial의 작성 정책을 알지 않는다. 생성 시 받은 Flag를 영속 연관관계로 추가할 필요는 없다.
- FlagInvitation도 생성 문맥인 Flag, 발신자 참여 정보, 수신자 참여·초대 존재 여부를 받아 판단한다. 애플리케이션은 사실을 준비하고 허용·거절 규칙을 대신 결정하지 않는다.
- Flag는 앵콜 생성 시 삭제되지 않은 기존 앵콜의 존재 여부를 boolean으로 받는다. canCreateEncore 같은 허용 결론이 아니라 hasExistingEncore라는 사실을 전달한다. 조회는 잠근 부모와 같은 트랜잭션에서 수행한다.
- MemorialFactory와 EncoreFactory는 복원하지 않는다. 규칙 수나 조회 row 수만으로 서비스를 추가하지 않고, 모델의 자연스러운 책임과 여러 호출 경로에서 공유할 연산이 있는지 판단한다. 잠금을 안다는 이유만으로 서비스를 제거하지도 않는다.

### 잠금·트랜잭션·이벤트의 기존 보장을 유지한다

후기 생성·삭제 및 앵콜 생성은 대상 Flag의 잠금 조회가 일반 조회보다 먼저다. 수동 삭제는 대상 Flag를 잠금 조회하고 앵콜이면 부모도 잠근다. 앵콜 → 부모 순서를 유지한다. 변경·저장·면제 재계산은 같은 트랜잭션에 둔다.

초대 수락의 READ_COMMITTED, 직접 참여의 트랜잭션 밖 친구 확인, 저장에 따른 도메인 이벤트 발행과 기존 비동기 후속 반응은 유지한다. 앵콜 자동 초대도 변경된 Invitation 생성 경로를 사용하되 대상 필터와 일괄 조회·저장을 유지한다.

## Out of Scope

- autoExpiryExempt 제거, 보존 점수 정책 변경, 애그리거트 통합, 참여·초대 자격의 제품 정책 변경
- FlagParticipationManager 및 FlagExpiryExemptionUpdater의 해체·재명명·저장 책임 확대
- 자동 만료 배치와 비동기 이벤트의 전달 보장 변경
- 자동 만료된 앵콜의 parent_id가 남아 DB 유니크 제약 때문에 퍼지 전 재생성을 막는 기존 문제. 삭제된 앵콜을 존재 조회에서 제외하는 동작은 유지·검증하지만, 이 task에서 스키마나 자동 만료 동작을 바꾸지는 않는다
- 다른 도메인의 Manager 일괄 해체 또는 조회·저장 배치 변경

## Acceptance Criteria

- Flag 도메인 서비스로 FlagParticipationManager와 FlagExpiryExemptionUpdater만 남고 네 Manager 및 그 의존이 제거된다. 같은 역할을 이름만 바꾼 서비스로 다시 만들지 않는다.
- Memorial과 Invitation의 생성 메서드가 필요한 Flag 상태와 자격을 직접 검사한다. Flag에는 Memorial·Invitation 생성 정책이 추가되지 않는다.
- Flag.createEncore가 직접 호스트·종료 상태·기존 앵콜 여부를 검사한다. 삭제된 앵콜은 존재 여부 조회에서 제외되며, 원천 데이터가 남는 DB 유니크 제약의 기존 제한과 구분한다.
- 직접 참여와 초대 수락이 같은 ParticipationManager를 사용하며 참여자 저장·삭제는 기존처럼 애플리케이션에 남는다.
- 후기·앵콜 변경 뒤 같은 Updater를 사용하고 Flag를 저장하여 면제 전이 이벤트가 유지된다.
- 후기 삭제의 Flag 선행 잠금, 앵콜 삭제의 대상 → 부모 잠금 순서와 기존 동시성 테스트가 유지된다.
- 기존 HTTP 계약, 개별 실패 조건의 오류 코드, 초대 권한 변경, 초대 수락·삭제 및 자동 초대가 유지된다. 여러 조건이 동시에 잘못된 입력의 예외 우선순위 변경은 구현 계획과 검증에서 명시한다.
- harness 아키텍처 문서에 모델·애플리케이션·공통 도메인 서비스의 배치 기준과 Flag의 적용 결과가 반영된다. 과거 task의 설계 결정은 당시 기록으로 보존한다.
