# Task-129: 자동 만료 면제를 바꾸는 경로가 모임 행을 먼저 잠근다

## Background

모임의 자동 만료 면제(`autoExpiryExempt`)는 후기와 앵콜의 존재로 정해지고, 판단 결과만 `Flag`에 저장한다. 면제가 맞지 않으면 후기가 달린 모임이 자동 만료로 지워진다. 점수 오차가 아니라 사용자가 쓴 데이터의 손실이다.

지금 이 값을 바꾸는 경로 어디에서도 모임 행을 잠그지 않는다. 코드로 확인한 경합이 셋 있다.

**자동 만료와 첫 후기가 겹친다.** `FlagExpiryService`는 대상을 조회한 뒤 `expireByIds`로 지운다. 이 UPDATE는 id와 `deleted_at`만 보고 면제를 다시 확인하지 않는다.

```text
스케줄러: 삭제 대상 조회          모임 A는 후기 없음, 면제 아님
사용자:   모임 A에 첫 후기 작성    면제가 켜지고 커밋
스케줄러: 대상 id로 삭제          면제를 다시 보지 않으므로 모임 A 삭제
```

후기가 달린 모임이 지워지고, 면제가 켜질 때(+15)와 자동 만료(+10) 점수가 둘 다 나간다.

**같은 모임의 후기 작업 둘이 겹친다.** 면제는 각 트랜잭션이 커밋 직전(`BEFORE_COMMIT`)에 남은 후기와 앵콜을 세어 정한다. 상대의 미커밋 변경은 보이지 않는다. 모임 A에 후기 M1이 있고 면제가 켜진 상태에서 시작한다.

```text
T1: 후기 M2 작성
T2: 후기 M1 삭제
T1: 남은 후기 확인 → M1, M2       면제 유지. 값이 그대로라 UPDATE가 나가지 않음
T2: 남은 후기 확인 → 없음          T1의 M2가 안 보임 → 면제 끔
T1, T2 커밋                       M2가 있는데 면제는 꺼짐
```

다음 스케줄러가 후기 M2가 있는 모임 A를 지운다. 앵콜 생성과 후기 삭제가 겹쳐도 같다.

**호스트 삭제와 첫 후기가 겹친다.** 호스트 삭제(`Flag.delete`)는 지우기 전에 면제를 끄고, 면제가 켜져 있었으면 회수(`PRESERVATION_RELEASED`) 이벤트를 낸다. `updateAutoExpiryExempt`는 메모리의 값과 같으면 아무것도 하지 않는다.

```text
호스트: 모임 A 조회               면제 false
사용자: 모임 A에 첫 후기 작성      면제 켜짐, +15 지급, 커밋
호스트: 모임 A 삭제               메모리 값이 false라 변화 없음 → 회수 이벤트 없음
```

`closeFlag`는 모임을 잠그지 않고 읽고, `Flag`에는 `@Version`이 없어 호스트의 UPDATE가 충돌로 실패하지도 않는다. 이 순서면 반드시 일어난다. +15가 회수되지 않고, `@DynamicUpdate`가 면제 컬럼을 쓰지 않아 삭제된 모임에 면제 true가 남는다.

## Objective

후기 작성·삭제, 앵콜 생성·삭제, 호스트 삭제가 같은 모임 행을 잠근 뒤 면제를 판단하거나 바꾸고, 자동 만료는 삭제할 때 면제를 다시 확인한다. 자동 만료나 같은 모임의 후기 작업이 겹쳐도 후기나 앵콜이 있는 모임이 지워지지 않고, 면제 값이 실제 후기·앵콜 유무와 어긋나지 않는다. 호스트 삭제와 첫 후기가 겹쳐도 면제가 켜진 모임을 지우면 회수 이벤트가 나간다. 각 경합은 동시성 테스트로 재현해 고정한다.

## Decision

### 비관적 잠금으로 막는다

같은 모임 행을 `findByIdForUpdate`로 잠근다. 잠금 대기는 같은 모임에서 작업이 실제로 겹칠 때만 생긴다. 일반 조회는 잠금과 무관해서 모임 조회와 목록은 느려지지 않는다.

새 잠금은 기존 잠금 경로와 마주치지 않는다. 참여, 초대 수락, 정원 변경, 일정 변경, 모집 마감은 종료 전에만 가능하고, 후기와 앵콜 생성은 `isEnded()`를 요구하며, 자동 만료는 종료 후 24시간이 지난 모임만 다룬다. 생명주기상 두 묶음이 같은 모임에서 겹치지 않는다. 후기 작업 트랜잭션에는 외부 호출이 없어 잠금 보유 시간도 짧다.

기각한 안:

- **낙관적 락(`@Version`).** 후기 작업끼리의 경합을 막으려면 면제를 판단하는 작업마다 버전을 강제로 올려야 한다(값이 그대로면 쓰지 않으므로). 그러면 같은 모임의 후기 작업은 겹칠 때마다 반드시 충돌하므로 동시성 이득이 없고, 실패 처리만 늘어난다. 버전이 모임 행 전체에 걸려, 부모 삭제 뒤 앵콜의 `parent_id`를 끊는 비동기 갱신처럼 면제와 무관한 쓰기와도 충돌한다. 지금은 `@Version` 없이 `@DynamicUpdate`로 바꾼 컬럼만 써서, 서로 다른 필드를 쓰는 경로가 서로를 덮거나 충돌하지 않는다.
- **조건부 갱신만 쓰고 후기 작업끼리의 경합은 감수.** 삭제 UPDATE에 면제 재확인을, 면제를 켜는 갱신에 "삭제되지 않은 경우에만"을 넣으면 잠금 없이 자동 만료와의 경합은 닫힌다. 후기 작업끼리의 경합은 남고, 남는 결과가 데이터 손실이라 감수하지 않는다.

### 잠금은 트랜잭션의 첫 조회여야 한다

InnoDB `REPEATABLE READ`에서는 첫 일반 조회가 읽기 시점을 고정하고, 잠금을 얻은 뒤에도 갱신되지 않는다(task-115에서 겪은 문제). 잠금 조회는 읽기 시점을 고정하지 않는다. 그러므로 각 경로는 일반 조회보다 잠금 조회를 먼저 해야 한다.

- 후기 삭제는 지금 후기를 먼저 읽는다. 요청의 `flagId`로 모임을 먼저 잠근다.
- 앵콜 삭제는 부모 id를 알려고 앵콜을 먼저 읽는다. 앵콜도 잠금 조회로 읽는다.

잠금과 면제 판단은 아래의 도메인 서비스 메서드 하나 안에 있다. 남는 규칙은 "그 메서드가 트랜잭션의 첫 호출이어야 한다"이다. 애플리케이션 서비스가 위임 전에 일반 조회를 하나 넣으면 컴파일과 단일 스레드 테스트를 통과한 채 경합이 다시 생긴다. 도메인 서비스에 호출 전제로 적고, 완료 기준의 동시성 테스트로 고정한다. 참여 경로가 이미 같은 방식(잠금이 트랜잭션의 첫 조회)이라 프로젝트 안에서 풀이가 하나로 맞는다.

기각한 안:

- **해당 경로만 READ COMMITTED.** RC에서는 일반 조회가 문장마다 최신 커밋을 보므로 순서 규칙이 필요 없다. 그러나 참여 경로는 task-127에서 잠금을 첫 조회로 옮기며 RC 지정을 뺐고, 지금은 먼저 초대를 읽어야 하는 초대 수락만 RC로 남아 있다. 같은 문제를 경로마다 다른 방법으로 푸는 상태에 예외를 다섯 개 더 얹게 된다.
- **면제 판단 조회를 잠금 조회(`FOR SHARE`)로.** 잠금 조회는 항상 최신 커밋을 읽어 순서와 무관해진다. 그러나 후기·앵콜 인덱스 범위에 넥스트 키 락이 걸려 잠금 범위가 넓어지고, 면제 판단에 쓰는 조회를 빠짐없이 바꿔야 한다.

### 잠금과 면제 판단은 도메인 서비스가 맡는다

면제에 영향을 주는 작업은 도메인 서비스 메서드 하나가 모임 잠금, 작업, 면제 재계산을 끝낸다. 애플리케이션 서비스는 트랜잭션을 열고 위임만 한다. 참여 경로의 `FlagParticipationManager`와 같은 모양이다.

- 후기 작성·삭제: `FlagMemorialManager`
- 앵콜 생성: `FlagEncoreManager`
- 호스트 삭제(앵콜 수동 삭제 포함): `FlagDeletionManager`

도메인 서비스가 잠금을 아는 것은 "면제 판단은 동시에 바뀌지 않는 최신 상태 위에서 한다"는 불변식의 요구라서다. 잠금이 `SELECT ... FOR UPDATE`라는 것은 어댑터가 안다. 첫 호출이어야 한다는 조건은 트랜잭션을 여는 애플리케이션 서비스가 지킨다.

커밋 직전 리스너로 면제를 갱신하던 구조는 걷어낸다. 같은 트랜잭션에서 동기로 도는 호출이었고, 이벤트 뒤에 숨어 잠금 순서와 첫 조회 조건이 드러나지 않았다. 후기 작성·삭제 이벤트는 면제 갱신 말고 쓰는 곳이 없어 함께 지운다. 면제 변화에 따른 점수, 앵콜 초대, 삭제 알림처럼 떨어져 있어도 되는 반응은 이벤트로 둔다.

### 앵콜 수동 삭제는 앵콜도 잠근다

앵콜 수동 삭제는 호스트 삭제와 같은 경로(`closeFlag`)다. 앵콜을 잠금 조회로 읽는 이유는 둘이다.

- 앵콜 자신의 면제. 앵콜에도 후기가 달리면 앵콜이 면제되고 보존 점수를 받는다. 호스트 삭제와 첫 후기가 겹치는 경합이 앵콜에도 그대로 생긴다.
- 부모의 면제. 부모 id를 알려면 앵콜을 먼저 읽어야 한다. 이 조회가 일반 조회면 읽기 시점이 고정되어, 부모를 잠근 뒤 세는 부모의 후기와 앵콜이 낡는다. 후기가 있는 부모의 면제가 꺼지고 다음 자동 만료에서 지워진다.

기각한 안:

- **이 경로만 READ COMMITTED.** 부모 판단이 낡는 문제는 풀리지만, 앵콜 자신의 면제를 지키려면 앵콜 잠금이 어차피 필요하다. 그 잠금 조회가 읽기 시점 문제도 함께 푼다.
- **부모 id만 먼저 다른 트랜잭션에서 읽기.** 참여 경로는 잠금 전에 외부 호출(친구 확인)이 있어 트랜잭션을 나눴다. 이 경로는 필요한 부모 id가 잠가야 할 앵콜 행에 있어 나눌 이유가 없다. 앵콜 삭제와 부모 면제 갱신은 한 트랜잭션이어야 하므로 나눌 수 있는 것도 부모 id 조회뿐이다.

### 교착은 잠금 순서로 막는다

부모와 앵콜을 함께 잠그는 경로는 앵콜 수동 삭제 하나이고, 순서는 앵콜 → 부모다. 부모 id를 알려면 앵콜을 먼저 읽어야 하기 때문이다. 부모를 쥔 채 앵콜을 잠그는 경로는 만들지 않는다.

현재 이 순서와 반대가 되는 경로는 없다.

- 부모 삭제: 앵콜의 `parent_id`를 끊는 일이 커밋 후 별도 트랜잭션(`FlagDeletionEventListener`)에서 돈다. 부모를 쥔 채 앵콜을 기다리지 않는다.
- 자동 만료: 잠금 조회를 하지 않는다. 삭제 UPDATE는 id로 대상 행만 잠그고, 면제된 부모는 대상이 아니라 잠그지 않는다.
- 앵콜 생성: 부모를 잠근 뒤 "이미 앵콜이 있는지"부터 확인하므로, 삭제 중인 앵콜 행을 기다리기 전에 거절된다.

앵콜 → 부모 순서는 `FlagDeletionManager`의 삭제 메서드 하나 안에 있다. 이 순서는 어겨도 데이터가 틀리지 않는다. InnoDB가 교착을 감지해 한쪽을 롤백하고 요청 하나가 실패한다. 그래서 주석에 기대지 않고 교착 테스트로 고정한다.

기각한 안:

- **부모 면제 갱신을 커밋 뒤 별도 트랜잭션으로.** 두 행을 함께 잡지 않게 되지만, 그 갱신이 따로 실패하면 앵콜이 없는 부모가 면제로 남아 영영 만료되지 않는다. 그래서 앵콜 삭제와 부모 면제 갱신을 한 트랜잭션으로 묶었다(커밋 `e419b9a`).

### 자동 만료는 삭제할 때 면제를 다시 확인한다

자동 만료는 잠금 조회를 하지 않는다. 대상 조회는 그대로 두고, 삭제 UPDATE에 `auto_expiry_exempt = false`를 더한다. UPDATE는 커밋된 최신 값으로 조건을 평가하고 후기·앵콜 작업은 모임을 먼저 잠그므로, 경우는 셋이다.

- 첫 후기가 UPDATE보다 먼저 커밋됨: 면제가 켜져 있어 지우지 않는다.
- 첫 후기 작업이 진행 중: UPDATE가 그 잠금을 기다렸다가 다시 확인하고 지우지 않는다.
- UPDATE가 먼저 지움: 후기 작성이 모임을 찾지 못해 실패한다.

후기나 앵콜이 있는 모임은 어느 경우에도 지워지지 않는다. 대신 앞의 두 경우에는 대상 조회 결과로 종료 이벤트가 나가, 면제로 받은 점수에 기본 점수가 한 번 더 얹힌다. 이 중복은 감수한다. 경합 창이 매시 정각 스케줄러 트랜잭션이 도는 짧은 순간뿐이고, 이 점수는 처음부터 정확히 한 번을 보장하지 않는 휴리스틱이다.

삭제 UPDATE에서 면제 조건을 뺀 것은 커밋 `9020a5d`다. 발행한 집합과 삭제한 집합을 맞추려는 선택이었고, 그 대가로 후기가 달린 모임이 지워질 수 있었다. 이번에는 데이터를 지키는 쪽을 우선한다.

기각한 안:

- **대상 조회를 잠금 조회로.** `end_date_time` 인덱스 범위를 훑는 잠금 조회는 REPEATABLE READ에서 조건에 맞지 않는 행까지 잠근다. 면제된 부모가 잠겨 앵콜 수동 삭제(앵콜 → 부모)와 반대 순서가 생긴다. 피하려면 후보를 고른 뒤 id로 다시 잠가야 한다. 얻는 것은 위의 점수 중복을 없애는 것뿐이라 비용이 크다.

### 부모 삭제 시 앵콜 링크 끊기는 비동기로 둔다

앵콜의 `parent_id`는 앵콜 자신의 면제 판단에 쓰이지 않는다. 링크가 늦게 끊겨도 점수 종류(앵콜 2배)와 초대 알림 문구 정도만 영향을 받고, 데이터 손실이나 불변식 위반은 없다. 반대 방향인 부모의 면제는 앵콜 유무로 정해지고 틀리면 데이터 손실이라, 앵콜 삭제만 부모를 잠근다.

## Out of Scope

- 자동 만료된 앵콜이 `parent_id`를 유지해 퍼지 전까지 같은 부모의 앵콜을 다시 만들 수 없는 문제
- 앵콜이 자동 만료될 때 부모를 갱신하지 않는 동작. 의도된 동작이다
- 만료된 앵콜이 `existsByParentId`에서 빠져, 이후 다른 이유로 부모의 면제 판단이 다시 돌면 면제가 풀릴 수 있는 문제. 보존 규칙(앵콜 존재 OR 후기 존재)을 바꾸지 않기로 했다
- 종료 이벤트의 유실, 멱등성 키, 아웃박스
- 후기 내용 수정. 면제에 영향을 주지 않는다

## Acceptance Criteria

- 자동 만료와 첫 후기가 겹치는 경우를 재현하는 동시성 테스트가 있다. 자동 만료가 대상을 고른 뒤 첫 후기가 커밋되면, 그 모임은 지워지지 않고 후기가 남는다. 수정 전 동작에서 실패한다.
- 같은 모임의 후기 작업 둘이 겹치는 경우를 재현하는 동시성 테스트가 있다. 같은 모임에서 후기 작성과 삭제가 겹쳐도, 커밋 뒤 후기가 남아 있으면 면제가 켜져 있다. 수정 전 동작에서 실패한다.
- 앵콜 생성과 부모의 후기 삭제가 겹쳐도 앵콜이 있는 부모의 면제가 꺼지지 않는다.
- 호스트 삭제와 첫 후기가 겹치는 경우를 재현하는 동시성 테스트가 있다. 호스트 삭제가 모임을 읽은 뒤 첫 후기가 커밋되면, 삭제 때 회수 이벤트가 나간다. 수정 전 동작에서 실패한다.
- 앵콜 삭제와 부모의 후기 작성을 동시에 실행해도 교착이 나지 않는다.
- 모임을 잠그는 각 경로에서 잠금 조회가 일반 조회보다 먼저 실행된다.
- 기존 `FlagParticipationLockConcurrencyIntegrationTest`, `FlagPreservationScoreScenarioTest`, 후기·앵콜·만료 관련 테스트가 모두 통과한다.
