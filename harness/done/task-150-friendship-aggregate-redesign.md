# Task-150: Friendship 애그리거트와 저장소 계약을 다시 세운다

## Background

Social을 MySQL로 이관한 뒤에도 Friendship 주변에는 이관 과정의 구조가 남아 있다. Task 149가 Social 전체를 한 번에 정리하려다 범위가 번져 취소됐고, 애그리거트 단위로 다시 나눈다. Friendship이 첫 단위다. 친구 요청 수락과 라벨 멤버 추가가 모두 Friendship에 기대기 때문이다.

현재 상태는 다음과 같다.

- 관계 생성 INSERT는 `ON DUPLICATE KEY UPDATE`로 중복 키를 성공으로 처리한다. Neo4j `MERGE`의 동작을 이어받은 것이다. 그래서 수락과 전송 경로가 관계를 `FOR UPDATE`로 먼저 확인한다.
- `FriendshipBroker`에는 `BiPredicate`를 받는 메서드와 사실(boolean)을 받는 메서드가 함께 있다. `Friendship`의 List 기반 `restore`와 `getRecognitions`도 남아 있다. 둘 다 470d489b가 계층별 전환을 위해 남긴 임시 경로이고, 영속 어댑터는 임시 경로만 쓴다.
- 사용자 쌍을 `"low_high"` 문자열로 만들어 저장소에 넘기면, 어댑터가 `UserPairKey.parse`로 다시 분해한다. 서비스, 어댑터, 테스트 여러 곳이 `Friendship.generateCompositeId`를 직접 부른다.
- 저장소 계약이 셋으로 나뉘어 있다. 도메인 `FriendshipRepository`, 이를 상속한 `FriendshipLifecycleRepository`, 일부 메서드를 다시 선언한 `FriendshipCreationRepository`다. 어댑터 하나가 셋을 모두 구현한다.
- 개인 설정 변경은 서비스가 원시 값을 저장소로 바로 넘기고, 별명 검증은 어댑터가 한다. `Friendship.updateUserFields`와 개별 설정 메서드를 부르는 곳은 없다.
- 감쇠는 `applyDecay` SQL이 일괄로 적용하고, `Friendship.decay`를 부르는 곳은 없다. 친밀도 계산식은 도메인과 SQL에 각각 있다.
- 도메인 `ArchivedFriendshipRepository`가 JPA 엔티티를 import해서 변환까지 한다.
- 서비스 이름에 이관 때의 접두사가 남아 있다(`MySqlFriendshipLifecycleService`, `MySqlFriendshipScoreService`). 점수 갱신 절차는 `FriendshipScoreUpdater`로 따로 떨어져 있다.

## Objective

Friendship 애그리거트와 저장소 계약이 하나의 모델로 정리된다. 사용자 쌍은 도메인 값으로 전달된다. 관계 규칙(생성 중복, 설정 검증, 점수와 친밀도)은 도메인이 소유하고, 저장소는 그 모델을 SQL로 옮기는 역할만 한다. 이미 친구인 쌍의 생성은 성공하지 않고 `AlreadyFriendsException`으로 끝난다. Friendship 서비스의 이름은 조회, 명령, 점수라는 책임에 맞춘다. 작업이 끝났을 때 Friendship에 관한 임시 호환 경로는 남지 않는다.

## Decision

- 애그리거트 하나를 단위로 도메인, 애플리케이션, 저장소를 함께 바꾼다. 계층별로 나눠 진행하는 방식은 기각한다. 470d489b가 그 방식으로 임시 호환 경로를 남겼고, 그 경로를 걷어내기 전에 범위가 번졌다.
- 작업이 끝난 시점은 배포 가능한 상태여야 한다. 기존 HTTP API의 경로, 입력, 응답, 권한과 노출 규칙을 보존한다.
- 스키마는 바꾸지 않는다. Flyway 마이그레이션을 추가하지 않는다.
- 중복 관계는 복합 기본 키가 막는다. 키 위반은 `AlreadyFriendsException`으로 바꾼다.
- 개인 설정은 관계를 로드해 `Friendship`이 바꾸고, 저장소는 본인 쪽 설정 열(별명, 음소거, 노출)만 쓴다. 대량 갱신 상황이 아니므로 도메인이 직접 바꾼다. 상대 쪽 열과 점수 열을 쓰지 않아서, 잠금 없이도 상대 설정과 점수 갱신을 잃지 않는다. 같은 사용자가 자기 설정을 동시에 두 번 바꾸면 나중 저장이 앞 저장을 덮어쓸 수 있는데, 드문 경우라 잠금을 걸지 않는다.
- 감쇠는 관심도를 깎고, 친밀도는 그 결과로 따라 깎인다. 정책 값(비율, 하한, 유예 기간)은 `FriendshipDecayPolicy`가, 적용 규칙은 `FriendRecognition.decay`와 `Friendship.decay`가 맡는다. 운영에서는 `applyDecay` SQL이 같은 정책 값을 받아 일괄 적용한다. 도메인 `decay`는 운영 경로에서 호출되지 않지만 감쇠 규칙의 정본으로 두고, 같은 입력에 대한 SQL 결과와 도메인 결과가 같은지 테스트로 확인한다. 기각한 대안은 도메인 `decay`를 지우고 SQL만 정본으로 두는 방식이다. 친밀도와 원칙이 갈리고, SQL이 어긋나도 잡을 기준이 없어진다.
- 관계는 문자열 ID 없이 사용자 ID로 식별한다. `Friendship.getId()`, `generateCompositeId`, Friendship과 라벨 어댑터의 문자열 분해(`UserPairKey.parse`)를 없앤다. 같은 형식의 요청 ID를 쓰는 친구 요청 어댑터의 분해는 요청 태스크에서 다룬다. 같은 사용자 두 명을 거부하는 검증은 지금처럼 `Friendship`의 생성과 복원이 맡는다. 저장소 포트는 사용자 ID를 순서와 무관하게 받고, low/high 정렬은 어댑터가 한다. 한 번에 여러 관계를 다루는 곳은 실제로 찾는 모양대로 받는다. 두 사람 사이, 한 사람과 여러 사람 사이(라벨 멤버 교체), 한 무리 안의 모든 관계(Flag 종료 점수 반영)다. 기각한 대안은 순서 없는 사용자 쌍 값 객체(`UserPair`)다. 검증은 이미 `Friendship`에 있어서 겹치고, 같은 사용자로 조회하는 호출(`areFriends(a, a)` 등)이 예외로 바뀌어 진입점마다 별도 처리가 필요해진다. ID 두 개로 조회하면 그런 호출은 지금처럼 "행 없음"으로 끝난다.
- `FriendshipBroker`는 Spring 없는 정적 클래스로 두고, 다른 애그리거트나 행의 존재 여부는 호출부가 조회해 사실로 넘긴다. Broker는 그 사실로 규칙("이미 친구면 요청도 관계 생성도 안 된다", "요청이 있으면 새 요청은 안 된다")을 판단한다. `BiPredicate`를 받는 `@Deprecated` 경로는 없앤다. 호출부가 사실을 조회하는 방식(잠금 여부 포함)은 지금과 같게 둔다.
- 점수 조정의 하한(0)과 마지막 교류 시각 갱신 규칙은 바꾸지 않는다. 음수 조정(`ScoreDirection.REVOKE`)을 쓰는 곳이 없어서 감쇠 하한과의 관계를 지금 정할 이유가 없다.
- 친밀도의 정본 규칙은 도메인에 둔다. 도메인은 친밀도를 필드로 들고 있지 않고 `getIntimacy()`가 두 관심도로 계산한다. `intimacy` 컬럼은 네트워크 조회의 정렬과 slice를 위해 유지하고, 관심도와 같은 문장에서 함께 갱신한다. 배치 SQL은 같은 식을 복제해 쓰고, 두 결과가 같은지는 테스트로 확인한다. 기각한 대안은 필드를 유지하고 `restore`에서 다시 계산하는 방식이다. 효과는 같지만 상태가 하나 더 남는다.
- `FriendRecognition`은 "내가 친구를 어떻게 인식하는가"(관심도, 별명, 음소거, 내 네트워크 노출 허용)를 담는다. 클래스 이름은 유지하고, 인식하는 사람을 가리키는 필드 이름을 `userId`에서 `ownerId`로 바꾼다. 기각한 이름은 `FriendshipSide`다. 위치만 말하고 담는 내용을 드러내지 못한다.
- 관심도는 스키마와 같이 null이 아닌 값(`double`)이다. `FriendRecognition`의 생성자는 package-private으로 둔다.
- Friendship 저장은 JDBC를 유지한다. 관계 한 행에 두 사용자의 설정과 시스템이 갱신하는 점수가 함께 있고, 셋은 동시에 독립적으로 바뀐다. 그래서 커맨드마다 자기 열만 쓰고 잠금 순서를 SQL로 정한다. 이 구조에서는 JPA의 이점을 쓰지 못하고 영속성 컨텍스트라는 관리 포인트만 늘어난다.
- 활성 사용자 판정은 저장소의 SQL 조건 하나(양쪽 사용자 모두 `ACTIVE`)로 통일한다. 프로필을 따로 조회해 메모리에서 거르던 조회와, 거르지 않던 존재 확인을 함께 맞춘다. 비활성 상대와의 관계는 조회, 잠금, 삭제에서 모두 없는 것으로 다룬다. 라벨 멤버 추가는 멤버의 활성 확인을 관계 잠금보다 먼저 해서, 비활성 친구를 추가하면 지금처럼 사용자 없음으로 끝난다.
- 친구 끊기는 관계 행을 먼저 지우고 라벨을 정리한다. DELETE가 잡는 배타 잠금이 라벨 멤버 추가·교체와의 순서를 정하므로 별도 잠금 조회를 두지 않는다.
- 아카이브 실행(스케줄러, 서비스, JPA 저장소)은 내린다. 아카이브된 관계를 어떻게 쓸지 아직 정하지 않았다. 도메인의 `FriendshipArchivePolicy`와 `ArchivedFriendshipRepository` 포트만 남긴다. 친밀도 하한에 닿은 관계는 자동으로 끝나지 않는다.

## Out of Scope

- 친구 요청의 수명 주기, 중복 규칙, 요청 테이블. 다음 태스크에서 다룬다. Broker는 임시 경로 제거와 시그니처 정리만 하고, 요청 서비스는 Friendship 계약과 Broker 시그니처가 바뀐 만큼만 호출부를 바꾼다.
- 전송, 수락, 라벨 멤버 추가 흐름의 `FOR UPDATE` 사용 여부. 사용자가 작업할 때 명시적으로 지시한다. 그 전까지는 지금의 잠금 동작을 유지한다.
- Label 모델과 멤버십 규칙. 라벨 서비스도 호출부만 바꾼다.
- 아카이브를 다시 실행하는 방식과 보관한 관계의 활용.
- 관계망, 중개인, 공개 프로필 서비스의 이름과 공개 포트. 이것들도 호출부만 바꾼다.
- 친구 요청과 라벨 서비스의 이름(`MySql` 접두사)과 구조. 각 애그리거트 태스크에서 다룬다.

## Acceptance Criteria

- `Friendship`과 `FriendshipBroker`에 `@Deprecated` 호환 경로가 없다. 영속 어댑터는 두 인식을 직접 바인딩하고 복원한다.
- Friendship의 저장소 계약은 하나다. 단건과 다건의 조회, 잠금, 삭제는 문자열 ID가 아니라 사용자 ID를 받는다. 같은 사용자 두 명으로 조회하면 지금처럼 예외 없이 "관계 없음"으로 끝난다.
- 이미 친구인 쌍을 생성하면 `AlreadyFriendsException`으로 끝나고, 기존 행의 설정과 점수는 변하지 않는다. 중복 관계 때문에 수락이 실패하면 요청이 보존되고 수락 이벤트는 발행되지 않는다.
- 별명 검증은 도메인에서 일어난다. 같은 행에서 양쪽 사용자의 설정 변경과 점수 갱신이 동시에 일어나도 서로의 변경을 잃지 않는다.
- 감쇠와 친밀도 규칙은 한 곳에서 정의된다. 감쇠는 지금처럼 SQL 일괄 갱신으로 적용되고, 같은 입력에 대한 결과가 기존과 같다.
- `social.domain` 패키지가 `adapter` 패키지를 import하지 않는다.
- 점수 갱신의 잠금 순서(PK 순서 `FOR UPDATE`), 일괄 저장, 새 트랜잭션과 재시도 동작이 회귀 테스트를 통과한다.
- Social, Buzz, Flag 테스트가 통과한다.
