# Task-128: Friendship HEX 패턴을 단일 FRIENDS_WITH 관계로 바꾸고 감쇄 스케줄러를 끈다

## Background

친구 관계 하나는 지금 `Friendship` 노드 1개와 `HAS_FRIENDSHIP` 관계 2개로 저장된다. HEX 패턴을 택한 이유는 셋이었다.

1. 잘못된 친구 관계가 원천적으로 존재할 수 없다. 한쪽만 관계를 걸어 두면 둘 다 친구로 인식되지 않는다.
2. 데이터 성격에 맞는다. 사용자별로 다른 값은 관계에, 공통 값은 노드에 담긴다.
3. SDN과 잘 맞는다. Spring Data Neo4j의 애그리거트는 노드만 다룬다.

그런데 Neo4j를 쓰는 이유는 조회 패턴이고, 지금 저장 모델은 조회 성능을 희생하고 있다. 조회 성능이 더 중요하다고 판단해 모델을 바꾼다. 단일 관계에서도 1번은 유지되고, 2번과 3번을 포기한다.

감쇄 정책은 앞으로 보강해야 해서, 그때까지 감쇄 스케줄러를 멈춰 둔다.

## Objective

친구 쌍 하나가 `FRIENDS_WITH` 관계 하나로 저장되고 `Friendship` 노드와 `HAS_FRIENDSHIP` 관계가 사라진다. `Friendship`과 `FriendRecognition`은 애그리거트로 남고, API 응답과 도메인 규칙은 바뀌지 않는다. 운영 데이터는 새 버전이 기동할 때 마이그레이션 파일로 이관된다. 감쇄 스케줄러는 기본으로 꺼진 상태가 되고 설정값을 넣으면 다시 켜진다.

## Decision

### 친구 쌍마다 관계 하나를 둔다

양방향 관계 두 개는 택하지 않는다. `intimacy`가 두 곳에 중복 저장되어 어긋나지 않게 유지할 책임이 생긴다.

### 방향과 속성

낮은 사용자 id가 시작 노드다. `id`, `createdAt`, `intimacy`는 관계에 하나씩 두고, 사용자별 필드 다섯 개(`friendAlias`, `interestScore`, `lastInteractedAt`, `isMuted`, `isRoutable`)는 `low`, `high` 접두사로 나눠 저장한다.

### 애그리거트 구조를 유지한다

`Friendship`과 `FriendRecognition`을 유지하고, 호출자가 사용자 id로 묻는 공개 메서드도 유지한다. `low`, `high`는 도메인에 들이지 않고 어댑터와 Cypher만 안다. 판별을 위해 메서드를 나누지 않는다.

관계는 SDN 애그리거트가 될 수 없으므로 두 클래스의 SDN 어노테이션을 걷어낸다. 어댑터가 관계와 양 끝 노드를 조립하고, 복원은 정적 메서드 `restore`로 한다. 이 경로는 `Neo4jClient`를 쓴다. SDN이 매핑하지 못하는 경우이기 때문이다.

### Friendship id를 관계 속성으로 저장한다

저장하지 않고 계산만 하는 안은 기각한다. 두 사용자로 관계를 찾으면 한쪽 인접 체인을 훑어야 해서, 점수 갱신마다 차수만큼 비용이 들고 Flag 종료 배치에서는 쌍 수만큼 곱해진다. id가 있으면 인덱스로 바로 찾고, 저장소 포트 시그니처도 바꾸지 않아도 된다. id는 생성 후 바뀌지 않으므로 인덱스 유지 비용은 친구 생성과 삭제 때만 든다.

`FRIENDS_WITH.id`에 유니크 제약을 건다. Aura에서 관계 유니크 제약이 되는지는 확인 전이고, 안 되면 일반 RANGE 인덱스로 간다.

### 락

`intimacy`는 양쪽 점수의 파생값이므로 점수를 읽기 전에 잠가야 한다는 조건은 그대로다. 잠금 대상만 `Friendship` 노드에서 `FRIENDS_WITH` 관계로 옮긴다. 여러 관계를 건드리는 쿼리의 정렬 키는 id를 유지한다.

### 친구 쿼리는 Cypher를 그대로 적는다

라벨과 속성을 상수로 조립하지 않는다. 시작점에서 관계를 타고 가는 조회 패턴이 드러나는 것을 우선한다.

속성 이름을 바꾸다 쿼리를 놓치면 에러 없이 `null`이 된다. 점수 쿼리는 `coalesce`로 0이 되어 `intimacy`가 덮어써지고, 아카이브가 그 친구 관계를 지울 수 있어 복구가 안 된다. 상수는 이 경로 중 쿼리 누락만 막고 오타, 이관 파일, 데이터 불일치는 못 막는다. 그래서 값을 검증하는 테스트와 속성 키 계약 테스트로 막는다. 배포가 테스트를 통과해야 진행되므로 운영에 나가기 전에 멈춘다.

### 비활성 사용자

비활성 사용자의 친구 관계는 보존한다. 재활성화하면 원상 복구되어야 하기 때문이다. id 인덱스로 찾더라도 사용자 대상 쿼리는 양 끝을 `:UserReference`로 매칭한다. 친구 관계 존재 확인과 삭제만 라벨을 보지 않는다.

이 규칙으로 동작이 둘 바뀐다. 둘 다 HEX 모델에서 재현해 확인한 결함이다.

- 친구가 비활성일 때 `findById`는 구성원이 하나뿐이라 `MappingException`을 던졌다. 이제 빈 결과를 돌려주어 `FriendshipNotFoundException`이 된다.
- 친구가 비활성일 때 감쇄는 활성 쪽 점수만 줄이고 `intimacy`를 지웠다. 이제 양 끝이 활성인 쌍만 감쇄하므로, 재활성화하면 값이 그대로 돌아온다.

### 이관은 Neo4j-Migrations로 한다

Flyway처럼 버전이 붙은 Cypher 파일을 앱 기동 때 실행한다. Flyway 자체는 공식 Neo4j 지원이 없고 커뮤니티 플러그인은 JDBC 드라이버가 따로 필요해서 택하지 않는다.

`deploy.sh`가 기존 컨테이너를 내린 뒤 새 컨테이너를 올리므로, 이관이 도는 동안 쓰기가 들어오지 않는다. `main` push가 곧 운영 배포이므로 이 순서가 배포와 이관의 시점을 맞춘다.

2.15는 `dbms.components()`가 두 행을 돌려주는 최신 Neo4j에서 기동에 실패해서 2.20을 쓴다.

노드 삭제 후에는 되돌릴 수 없다. 배포 전에 Aura 스냅샷을 받고, 로컬의 Neo4j Desktop `dev` DB에서 먼저 실행해 본다.

### 감쇄 스케줄러는 설정으로 끈다

코드를 지우지 않고 cron을 설정값으로 빼서 기본값을 비활성으로 둔다. 정책 보강 후 설정값만 넣으면 다시 켜진다. 감쇄 쿼리는 남으므로 함께 단일 관계로 옮긴다. 아카이브 스케줄러는 끄지 않는다.

## Out of Scope

- 관심도 delta, 친밀도 공식, 관계망 노출 규칙의 변경
- 감쇄 정책 보강
- 로컬 Neo4j 환경 전환

## Acceptance Criteria

- `Friendship` 노드와 `HAS_FRIENDSHIP`을 쓰는 코드가 남아 있지 않다.
- `Friendship`과 `FriendRecognition`에 SDN 어노테이션이 없고, 도메인에 `low`, `high`가 드러나지 않는다.
- 관계망, 연결 경로, 앵커 확장, 뮤트 조회가 같은 입력에 기존과 같은 결과를 돌려준다.
- 단방향, 상호, 배치 점수 갱신 결과가 도메인 참조 구현과 일치한다.
- 같은 친구 쌍을 양쪽에서 동시에 갱신해도 점수가 유실되지 않고, `intimacy`가 최종 점수로 계산된다.
- 규약을 어긴 쿼리로 교착이 재현되고, 현행 쿼리들로는 같은 조건에서 교착이 나지 않는다.
- 같은 친구 쌍의 `FRIENDS_WITH` 관계가 둘 이상 생기지 않는다.
- 모든 쓰기 경로를 실행한 뒤 관계의 속성 키가 정해진 목록과 정확히 같다.
- 비활성화했다가 재활성화하면 친구 관계와 사용자별 필드가 원상 복구된다.
- HEX 데이터에 마이그레이션을 실행하면 친구 쌍 수, id, `createdAt`, `intimacy`, 사용자별 필드 값이 이관 전과 일치하고 `Friendship` 노드가 남지 않는다. 비활성 사용자의 친구 관계도 포함한다.
- 마이그레이션을 다시 실행해도 데이터가 바뀌지 않는다.
- 마이그레이션이 Neo4j Desktop `dev` DB에서 성공한다.
- 설정값이 없으면 감쇄 스케줄러가 돌지 않고, 설정값을 넣으면 그 주기로 돈다.
