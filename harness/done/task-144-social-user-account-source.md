# Task-144: 소셜 사용자 조회를 MySQL 계정 원본으로 옮긴다

## Background

계정의 사용자 ID·닉네임·프로필 이미지·활성 상태를 Neo4j의 `SocialUser`에 복제한다. 계정 변경은 Outbox를 거쳐 반영하고, 조회 시 노드가 없으면 Lazy Sync로 복제한다. 활성 상태가 이벤트 도착 순서에 따라 어긋날 수 있다.

## Objective

MySQL로 이전한 Social 기능이 프로필과 활성 상태를 Account의 원본에서 읽을 수 있게 한다. 기존 소셜 프로필 응답과 도메인 간 의존 방향을 유지하면서, Social 데이터가 참조할 사용자 ID를 계정 ID로 통일한다.

## Decision

- 소셜 사용자 전용 프로필·활성 상태 복제본을 새로 만들지 않는다. 계정이 상태와 표시 정보의 원본이다. 여러 사용자 정보가 필요하면 ID 목록으로 조회할 수 있어야 한다.
- 기존 Account 조회 포트와 일괄 조회를 재사용한다. MySQL 원본을 읽는 `AccountSocialUserQueryService`는 기존 소셜 프로필 응답과 조회 실패 예외를 사용한다.
- 소셜 프로필 API는 Social 읽기·쓰기 전환 시 계정 원본 조회에 연결한다. 그때 사용자 동기화를 제거한다.
- MySQL 저장소 테스트는 MySQL 전용 컨테이너 설정을 사용한다.

## Acceptance Criteria

- MySQL 경로의 소셜 프로필은 동일한 사용자 ID·닉네임·프로필 이미지로 기존 응답 계약을 충족한다.
- 계정 상태가 바뀌면 MySQL 경로의 사용자 노출에 반영된다. 비활성 사용자가 계정 원본과 다르게 노출되는 복제 상태가 생기지 않는다.
- 여러 사용자의 정보를 요청하는 Social 호출을 사용자별 반복 조회 없이 처리할 수 있다.
