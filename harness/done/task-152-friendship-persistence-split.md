# Task-152: Friendship 저장을 애그리거트 단위와 집합 단위로 나눈다

## Background

task-150은 Friendship 저장 전체를 JDBC로 유지했다. 근거는 Friendship 전체를 JPA로 옮기면 쓰기와 잠금 대부분이 네이티브 쿼리로 남고 영속성 컨텍스트라는 관리 포인트만 늘어난다는 것이었다. 이 판단은 저장 경로 전체를 한 기술로 옮기는 경우를 전제로 했다.

FriendRequest 태스크를 논의하면서 경로별로 기술을 나누는 기준이 나왔다. 애그리거트 하나를 로드해 도메인이 검증하고 저장하는 경로는 JPA가, 여러 행을 순서대로 잠그거나 한 문장으로 읽고 바꾸는 경로는 JDBC가 맡는다.

지금 저장소 계약은 도메인 `FriendshipRepository` 하나다. 애그리거트 저장과 잠금 조회, 일괄 갱신, ID 목록 조회가 한 포트에 함께 있다. 정렬용 `intimacy` 열은 생성·점수 저장·감쇠 SQL이 각자 계산해 쓴다.

## Objective

Friendship의 애그리거트 단위 경로는 JPA 매핑으로, 집합 단위 경로는 JDBC로 구현된다. 잠금과 집합 갱신은 애플리케이션 포트로 옮겨 도메인 포트에는 애그리거트 저장만 남는다. `intimacy` 열은 DB가 두 관심도로 계산한다. 기존 HTTP API와 동시성 보장(설정 변경은 본인 쪽 열만 쓴다, 점수 갱신은 PK 순서로 잠근다, 끊기는 관계 삭제를 라벨 정리보다 먼저 한다)은 유지된다.

## Decision

- 경로를 이렇게 나눈다.
  - JPA(애그리거트 단위): 생성, 두 사람 사이 단건 조회, 내 친구 목록, 설정 변경, 친구 끊기, 친구 존재 확인. 존재 확인은 Broker에 넘길 도메인 사실이라 도메인 포트에 남고, 그 포트를 구현하는 JPA 어댑터가 네이티브 쿼리로 맡는다.
  - JDBC(집합 단위): 점수 갱신의 잠금 조회와 일괄 저장, 감쇠, 라벨 멤버 추가·교체의 잠금 조회, Buzz용 친구 ID 조회
- 잠금이 유스케이스끼리의 순서 조율이나 집합 갱신을 위한 것이면 잠금 조회는 `application/port/out`에 둔다. Friendship의 잠금은 모두 이 경우다. 점수 갱신의 잠금은 집합 갱신이 엇갈리지 않게 하려는 것이고, 라벨 경로의 잠금은 다른 애그리거트(Label)와 친구 끊기의 순서를 맞추려는 것이다. Friendship 자신의 규칙이 도는 경로(생성, 설정 변경, 끊기)에는 잠금이 없다. 그래서 도메인 `FriendshipRepository`에는 애그리거트 저장과 조회만 남기고, 잠금 조회·일괄 저장·감쇠·ID 조회는 애플리케이션 포트로 옮긴다. task-150의 "저장소 계약은 하나"는 겹치던 계약을 정리하려는 목적이었고, 이번 분리는 겹침 없이 책임으로 나눈다.
- 애플리케이션 포트는 도메인 포트를 상속하지 않는다. 상속하면 점수 서비스가 생성과 삭제까지 부를 수 있어 책임 경계가 흐려진다. 포트 넷은 어댑터 하나(`FriendshipPersistenceAdapter`)가 구현하고, 쿼리는 기술별 저장소(`jpa/FriendshipJpaRepository`, `jdbc/FriendshipJdbcRepository`)에 둔다. 어댑터는 포트 이름과 저장소 메서드 사이의 번역, 키 정렬, 키 중복의 예외 변환만 한다. 한 애그리거트가 두 기술을 쓰므로 어느 포트 메서드가 어느 기술을 쓰는지 한 클래스에서 보이게 하려는 것이다. 기각한 대안은 기술별 어댑터 둘(JPA 어댑터가 도메인 포트, JDBC 어댑터가 애플리케이션 포트)이다. 포트 구현이 기술 기준으로 흩어지고, 경로 하나를 다른 기술로 옮기면 구현 클래스가 바뀐다. 한 기술만 쓰고 번역이 없는 조회 포트(SocialNetwork 등)는 기술 저장소가 포트를 직접 구현한다. 두 기술의 활성 쌍 조건은 `FriendshipConditions` 상수 하나를 함께 쓴다.
- 도메인 클래스 `Friendship`을 그대로 엔티티로 쓰고 `FriendRecognition`은 값 타입으로 매핑한다. JPA는 값 타입 안의 필드를 키로 쓸 수 없으므로 `Friendship`에 비공개 키 필드 두 개를 두고 `@IdClass`로 매핑한다. 키 필드는 생성과 복원 때 두 인식에서 한 번 채우고 바꾸지 않는다. 인식의 `ownerId`는 같은 열에 읽기 전용으로 매핑하고, 도메인 로직은 지금처럼 인식의 `ownerId`를 쓴다. 두 인식은 `low_*`, `high_*` 열에 접두사로 매핑한다.
- `intimacy` 열은 두 관심도로 DB가 계산하는 `STORED` 생성 열로 바꾼다. 친밀도 규칙의 정본은 도메인 `getIntimacy()`이고, 생성 열의 식은 정렬을 위한 사본이다. 같은 입력에서 둘이 같은지는 테스트로 확인한다. JPA는 이 열을 매핑하지 않고, JDBC 점수 저장과 감쇠 SQL에서도 친밀도 쓰기가 빠진다. 열을 바꾸는 순간 기존 행이 점수 기준으로 다시 계산되어 열과 점수가 어긋난 행이 남지 않는다. 기각한 대안은 `getIntimacy()`에 열을 매핑하고 애플리케이션이 계속 쓰는 방식이다. 스키마는 그대로지만 친밀도 계산이 JPA·점수 저장·감쇠 세 곳에 남는다.
- 설정 변경은 관계를 읽어 도메인이 바꾸고 더티 체킹으로 저장한다. 엔티티에 `@DynamicUpdate`를 붙여 바뀐 열만 UPDATE한다. 한 행을 두 사용자와 점수 갱신이 잠금 없이 동시에 서로 다른 열로 고치므로, 기본 UPDATE(모든 열)면 서로의 변경을 덮어쓴다. 도메인에는 `jakarta.persistence` 표준 어노테이션만 두는 것이 원칙이지만, 이 행의 동시성 보장을 맡는 `@DynamicUpdate`는 예외로 둔다. Hibernate는 값 타입을 속성 하나로 비교하므로, 한쪽 인식의 설정이 바뀌면 그쪽 열이 점수까지 함께 쓰인다. 그래서 관심도와 마지막 상호작용 시각 열은 `updatable = false`로 매핑해 JPA가 쓰지 못하게 한다. 점수는 JDBC 포트만 쓴다. 기각한 대안은 읽기 전용으로 조회한 뒤 네이티브 UPDATE로 본인 쪽 열을 쓰는 방식이다. 같은 보장을 얻지만 저장 메서드와 조회 힌트가 필요하고, 힌트가 빠지면 네이티브 쿼리 직전의 자동 flush가 전체 열 UPDATE를 보낸다.
- 친구 끊기는 엔티티 `remove`가 아니라 즉시 실행되는 삭제 쿼리(`@Modifying`)로 한다. `remove`는 DELETE를 커밋 때 보내므로, 즉시 실행되는 라벨 정리(JDBC)보다 늦어져 "관계 삭제를 먼저 해 그 행의 배타 잠금으로 라벨 멤버 추가와 순서를 맞춘다"는 task-150의 보장이 깨진다. 삭제 쿼리는 양쪽 활성 조건을 유지하고, 건수 0이면 관계 없음이다.
- 관계 생성은 `persist` 직후 flush해서 키 중복을 그 자리에서 `AlreadyFriendsException`으로 바꾼다. Spring Data `save`는 키가 채워진 엔티티를 merge로 다뤄 기존 행을 덮어쓰므로 쓰지 않는다.
- 저장소와 어댑터에는 `@Transactional`을 두지 않는다. 트랜잭션 경계는 애플리케이션 서비스가 정한다. 저장소를 트랜잭션 밖에서 직접 부르는 테스트는 `TransactionTemplate`으로 감싼다.
- JPA 조회의 활성 사용자 조건은 네이티브 쿼리에 SQL로 둔다. 활성 상태는 Account의 `users`에 있어 JPQL로는 Account 엔티티를 참조해야 한다.
- 한 트랜잭션 안에서 JPA로 바꾸고 아직 flush하지 않은 테이블을 JDBC로 읽거나 쓰지 않고, JDBC로 쓴 테이블을 JPA로 다시 읽지 않는다. 영속성 컨텍스트는 트랜잭션마다 새로 생기므로 이 두 경우만 메모리와 DB를 어긋나게 한다. 앵커 추천처럼 같은 테이블을 두 기술로 읽기만 하는 경우와, 수락처럼 JDBC로 먼저 읽고 JPA로 쓰는 경우는 허용한다.

## Out of Scope

- FriendRequest와 Label의 저장 방식. 각 애그리거트 태스크에서 다룬다. 요청 수락의 관계 잠금 조회는 task-151에서 정리할 때까지 지금처럼 둔다.
- `ARCHITECTURE.md` §2의 저장소 사용 전략 개정. 다른 애그리거트에서 기준을 더 확인한 뒤 정한다.
- Flag의 잠금 배치와 `ARCHITECTURE.md` Flag 책임 표의 정리. 사용자가 따로 검토한다.

## Acceptance Criteria

- 도메인 `FriendshipRepository`에는 생성, 단건 조회, 친구 목록, 친구 끊기, 친구 존재 확인만 있다. 잠금 조회·일괄 저장·감쇠·ID 조회는 애플리케이션 포트에 있고, 두 포트는 서로 상속하지 않는다.
- 설정 변경은 본인 쪽 설정 열만 갱신한다. 같은 행에서 양쪽 사용자의 설정 변경과 점수 갱신이 동시에 일어나도 서로의 변경을 잃지 않는다.
- 친구 끊기는 관계 삭제가 라벨 정리보다 먼저 실행되고, 라벨 멤버 추가·교체와의 동시성 테스트가 통과한다.
- `intimacy` 열은 DB가 계산하고, 같은 입력에 대한 도메인 `getIntimacy()`와 열 값, SQL 감쇠 결과와 도메인 감쇠 결과가 같다.
- 점수 갱신의 잠금 순서, 일괄 저장, 새 트랜잭션과 재시도 동작이 회귀 테스트를 통과한다.
- task-150 Decision의 JDBC 유지 근거와 포트폴리오 문서 「관계는 한 행에, 쓰기는 주인별로」의 "대가" 절이 바뀐 판단에 맞게 고쳐진다.
- Social, Buzz, Flag 테스트가 통과한다.
