# Task-145: 친구 관계와 친구 요청을 MySQL로 옮긴다

## Background

친구 요청을 수락하면 요청이 사라지고 친구 관계가 만들어진다. 두 변경은 현재 하나의 Neo4j 트랜잭션에서 실행된다. 친구 관계에는 공동 친밀도와 두 사람 각각의 값이 함께 저장된다.

## Objective

MySQL 계정의 사용자 ID를 참조하는 친구 관계와 친구 요청의 저장·조회 경로를 구현한다. 기존 친구 요청 상태 전이, 양쪽 친구 목록, 설정, 상호작용에 따른 친밀도 갱신과 감쇠를 유지한다.

## Decision

- 친구 관계는 작은 ID를 먼저 둔 `(low_user_id, high_user_id)` 복합 키 한 행으로 저장한다. 어느 사용자를 기준으로도 인덱스로 조회할 수 있어야 한다.
- `intimacy`는 관계당 하나를 저장한다. 관심도, 친구 별명, 마지막 교류 시각, 음소거, `isRoutable`은 같은 관계에서 사용자별로 보존한다. 관심도와 공동 친밀도는 함께 갱신한다.
- 사용자 설정은 요청한 쪽의 전달된 컬럼만 단일 `UPDATE`로 바꾼다. 시스템 상호작용은 기존 관심도를 읽고 계산하므로 복합 키 순서로 관계를 잠그고, 계산과 일괄 저장을 같은 MySQL 트랜잭션에서 수행한다.
- 한 쌍의 친구 요청은 DB 유일성 제약으로 하나만 허용한다. 요청을 보낸 사람과 받은 사람의 방향은 별도로 유지한다.
- 사용자 프로필은 Social의 읽기 SQL이 MySQL의 `users`에서 조회한다. 계정의 쓰기는 Account가 담당한다.
- 현재 감쇠 공식·하한·스케줄 설정과 기존 MySQL의 아카이브 기록을 보존한다. 감쇠 후 활성 관계를 없애는 아카이브 명령은 라벨 멤버십 정리와 같은 트랜잭션으로 연결할 때 전환한다.

## Acceptance Criteria

- A에서 B로, B에서 A로 조회해도 같은 관계와 친밀도가 반환되고 별명·공개 여부 등은 조회 방향에 맞는다.
- A→B와 B→A의 요청을 동시에 보내도 한 쌍의 요청은 하나만 남는다. 수락 후에는 친구 관계 하나가 존재하고 요청은 사라진다. 수락 실패 시 두 변경이 함께 롤백된다.
- 요청 조회·숨김·취소·정리와 친구 목록·설정 변경이 기존 API 의미를 유지한다.
- 단방향·양방향 관심도 갱신과 감쇠가 기존 계산 결과를 유지한다. 동시에 양쪽의 관심도가 바뀌어도 먼저 반영된 변경을 덮어쓰거나 친밀도가 최종 관심도와 어긋나지 않는다.
