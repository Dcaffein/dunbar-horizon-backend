# Issue Guide

GitHub Issue는 사용자와 합의한 작업을 기록한다. 논의와 실행 시점을 분리하여 다른 세션에서도 작업을 이어받을 수 있게 하고, 구현 후에는 당시의 의도와 선택 이유를 찾을 수 있게 한다.

Issue 본문은 목적, 요구사항, 설계 결정, 범위와 완료 조건의 정본이다. PLAN은 이를 현재 코드에 적용할 커밋 단위와 검증 방법을 정한다. 합의된 설계를 PLAN에서 다시 서술하지 않는다.

## 제목과 기본 구조

제목은 작업 대상과 달성하려는 변화를 구체적으로 표현한다. 예: `도메인 실패 이유와 HTTP 오류 매핑을 분리한다`.

다음 다섯 섹션을 기본 구조로 사용한다. Objective와 Acceptance Criteria는 필수이며, 나머지는 해당 내용이 있을 때 작성한다. 형식을 채우려고 내용을 만들거나 같은 설명을 반복하지 않는다. API 계약, 상태 전이표, 재현 절차 등 이해에 필요한 표와 하위 섹션을 추가할 수 있으며, 별도 섹션이 더 읽기 좋으면 추가해도 된다.

| 섹션 | 작성할 내용 |
|------|-------------|
| Background | 어떤 상황과 문제가 논의를 시작하게 했는가. 당시 코드와 제약, 필요한 경우 재현 조건과 영향을 기록한다. 확인한 사실과 추측을 구분한다. |
| Objective | 완료되면 무엇이 달라지는가. 작업의 도착점을 짧게 설명한다. 상세 설계와 모든 제약을 압축해 반복하지 않는다. |
| Decision | 사용자와 합의한 설계와 그 이유. 검토한 대안과 기각 이유, 의도적으로 감수한 한계를 함께 기록한다. |
| Out of Scope | 관련은 있지만 이번 작업에서 다루지 않을 범위. 후속 Issue가 있으면 연결한다. |
| Acceptance Criteria | 무엇을 확인하면 완료인가. 동작, 구조, 데이터, 동시성 등 작업에 필요한 조건을 검증 가능한 문장으로 쓴다. |

## 맥락과 결정 기록

- 대화 내용을 그대로 옮기지 않고, 다른 세션이 본문만 읽어도 현재 합의와 이유를 이해할 수 있게 정리한다. 중요한 근거가 댓글에만 남지 않게 한다.
- Background는 문제의 출발점을, Decision은 해결책을 선택한 이유를 설명한다. 특정 결정만을 뒷받침하는 근거는 그 결정 옆에 둔다.
- 합의한 설계는 클래스, 메서드, 쿼리 수준까지 구체적이어도 된다. 나중에 "왜 이렇게 구현했는가"를 설명하는 데 필요한 결정은 구현 세부사항이라는 이유로 제외하지 않는다.
- Decision의 각 항목은 선택과 이유를 함께 읽을 수 있게 쓴다. 긴 문단에 여러 결정을 묶지 말고 필요하면 업무 주제별 소제목으로 나눈다.
- "이번에는 다루지 않는다"는 Out of Scope에, "검토했지만 선택하지 않는다"는 Decision에 이유와 함께 기록한다. 후속 작업과 기각한 대안을 혼동하지 않는다.
- 당시 사실을 기록할 때 현재 코드에도 영구히 적용되는 설명처럼 쓰지 않는다. 의도 이해에 필요한 코드나 이전 작업은 관련 커밋·Issue 링크로 근거를 남길 수 있다.

## PLAN과의 경계

- Issue에는 합의된 요구사항과 설계 결정을, PLAN에는 코드 탐색에서 추가로 확인한 사실과 커밋별 변경 범위·검증·부작용을 둔다.
- 단순한 변경 파일 목록, 커밋 순서, 테스트 실행 명령을 Issue에 반복하지 않는다. 다만 특정 검증 방식 자체가 합의된 제약이면 기록한다.
- Acceptance Criteria는 단순히 "테스트가 통과한다"로 끝내지 않는다. 예를 들어 "동시 댓글 작성이 서로의 변경을 덮어쓰지 않는다"처럼 확인할 결과를 적는다. 구조 리팩토링은 의존 방향이나 계약의 위치도 완료 조건으로 둘 수 있다.
- 버그 수정은 해당 문제가 해결됐음을 확인할 재현 조건과 기대 결과를 명시한다. PLAN에서 회귀 테스트가 수정 전 동작에서는 실패하는지 확인할 방법을 정한다.

## 설계 변경과 갱신

- Issue의 확정된 요구사항·설계·범위는 에이전트가 임의로 변경하지 않는다.
- PLAN 수립 또는 구현 중 번복이 필요하면, 기존 결정과 충돌하는 코드 근거, 유지할 경우의 문제, 영향과 대안을 보고하고 해당 결정에 의존하는 작업을 멈춘다.
- 사용자와 Issue 재논의 단계로 전환한다. 다른 세션에서 논의할 수 있으므로 근거와 쟁점을 전달할 수 있게 정리한다.
- 합의 후에는 Issue 본문을 갱신한다. 이 단계의 결과물은 갱신된 Issue이며, 이를 PLAN 재작성이나 구현 재개의 승인으로 간주하지 않는다. 재개는 사용자의 지시에 따른다.
- 본문에는 현재 합의를 명확하게 두되, 중요한 이전 대안과 번복 이유를 Decision에 남긴다. 이전 결정을 현재 결정처럼 병렬로 나열하거나, 과거 이유를 지워 의사결정 맥락을 잃지 않는다.

## 구현 이력과의 연결

- 구현 커밋이나 PR에서 관련 Issue를 연결하여 코드 변경에서 당시 의도로 찾아갈 수 있게 한다.
- 실제 변경과 검증 결과는 커밋·PR 및 완료 보고에 기록한다. Issue의 설계 본문을 변경 파일 목록이나 작업 일지로 바꾸지 않는다.
- 동일한 발주서를 로컬 TASK와 Issue 양쪽에서 관리하지 않는다. 기존 TASK를 이전한 경우 Issue를 정본으로 정하고 원본 기록과 연결한다.

## 본문 양식

내용이 없는 선택 섹션은 생략한다.

```markdown
## Background

## Objective

## Decision

## Out of Scope

## Acceptance Criteria
```
