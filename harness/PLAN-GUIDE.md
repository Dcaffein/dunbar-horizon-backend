# Plan Guide

PLAN은 Issue의 합의를 현재 코드에 적용할 실행·검증 계획이다. Issue의 목적, 배경과 설계 이유를 다시 쓰지 않는다. `PLAN.md`는 작업마다 갱신하는 로컬 실행 문서로 Git에 추적하지 않는다.

## 기본 구조

제목에 Issue 번호와 작업명을 쓰고 Issue URL과 기준 브랜치를 기록한다. 다음 세 섹션을 사용한다.

### 실행 전 확인

- Issue의 전제와 현재 코드가 다른 부분, 추가로 확인한 영향 범위, 실행 전에 해결할 사항을 적는다. 차이가 없다면 짧게 명시한다.
- 확정된 설계·요구사항·범위를 바꿔야 한다면 계획을 확정하지 않고 WORKFLOW의 Issue 재논의 절차를 따른다.

### 커밋 단위 계획

각 단위는 따로 검토하고 되돌릴 수 있는 범위로 나누며 다음을 적는다.

- 변경 목적과 범위: 관련 파일·구성 요소와 할 일.
- 함께 변경해야 하는 이유와 선행 단위: 컴파일, 데이터 전환 등 필요한 의존 관계.
- 검증 방법: 관련 테스트와 확인할 결과. 버그 수정은 수정 전 실패를 확인할 회귀 검증을 포함한다.
- 주의할 부작용: API, 데이터, 잠금·트랜잭션, 다른 모듈 등에 미치는 영향과 대응.

쿼리·시그니처는 잠금, 성능, 외부 계약 등을 검토하는 데 필요한 경우 구체적으로 쓴다. 모든 구현을 코드처럼 미리 옮겨 적지 않는다. 변경 규모에 맞춰 상세도를 조절하고, 해당하지 않는 항목은 생략한다.

### 완료 검증

개별 커밋의 검증만으로 확인되지 않는 Issue 완료 조건과 최종 확인 방법을 적는다. 이미 각 단위에서 충분히 검증하는 항목은 반복하지 않는다.

## 갱신

- 실행 중 순서·범위·검증 방법이 조정되면 PLAN을 최신 상태로 갱신한다.
- Issue의 합의를 번복하는 결정을 PLAN에만 적어 진행하지 않는다. 사용자와 재논의하여 Issue를 갱신하고, 재개 지시를 받은 뒤 계획을 다시 수립한다.
- 중요한 변경은 발생 시점에 보고하고 관련 커밋에 이유를 남긴다. PLAN은 과거 결정의 정본이나 작업 완료 이력이 아니다.
