# Task-149: Social 애플리케이션과 저장소 구조를 정리한다

> 취소 · Social 전체를 한 태스크로 묶어 범위가 요청 수명 주기·스키마 변경까지 번졌다. 애그리거트 단위 태스크(Friendship → FriendRequest → Label)로 다시 발주한다.

## Background

Social의 읽기와 쓰기가 MySQL로 통합된 뒤에도 애플리케이션 서비스에 이관 당시의 `MySql`, `Account` 이름과 저장소의 중복 인터페이스가 남아 있다. 친구 수락은 이미 친구인 경우를 오류로 처리하지만, 관계 생성 쿼리는 기존 Neo4j `MERGE`의 동작을 이어받아 중복 키를 성공으로 처리한다. 내부 컨트롤러용 `UseCase`와 Buzz·Flag가 호출하는 계약도 같은 방식으로 노출돼 있어 모듈 밖에서 쓰는 동작을 찾기 어렵다.

## Objective

Social 서비스의 이름과 책임을 실제 유스케이스에 맞추고, 도메인 규칙을 MySQL의 복합 키·제약·트랜잭션으로 표현한다. 모듈 간 계약을 정리하고 기존 HTTP API, 조회 정책, 쓰기 정합성을 유지한다.

## Decision

- 친구 요청의 목록 조회와 전송·취소·상태 변경은 `FriendRequestService`에 둔다. 만료된 숨김 요청을 처리하는 `FriendRequestCleanupService`는 독립된 예약 작업으로 유지한다.
- 친구 관계는 역할 차이가 큰 `FriendshipQueryService`와 `FriendshipCommandService`로 구분한다. 명령 서비스는 개인 설정 변경, 친구 끊기, 아카이브를 맡는다. 이벤트에 따른 점수 반영과 감쇠는 `FriendshipScoreService`에 두고, 현재 점수 서비스만 사용하는 갱신 흐름도 이곳에 둔다.
- `LabelService`는 라벨과 멤버십의 조회·변경을 함께 맡는다. Social 내부 컨트롤러는 이 서비스를 직접 호출하고, Buzz는 `LabelQueryUseCase.getMemberIdsByLabels`를 통해 수신자 ID를 조회한다.
- `SocialNetworkQueryService`는 관계망, 대상 연결, 공통 친구 경로 조회를 맡는다. 내가 고른 친구를 기준으로 후보를 확장하거나 추천하는 기능의 이름은 `IntermediaryNetworkService`로 한다.
- 공개 프로필은 `SocialProfileQueryService`에서 활성 계정과 이미지 URL을 조회해 응답한다. Social 내부 컨트롤러가 사용하는 기능은 서비스를 직접 호출하고, 다른 모듈이 소비하는 기능은 입력 포트로 공개한다.
- 저장소 인터페이스의 중복 상속과 선언을 정리한다. `FriendshipRepository`는 개별 친구 관계와 그 행의 조회·잠금·갱신을 맡는다. 관계망 구성, 공통 친구 경로, 중개인 기준 후보 탐색처럼 여러 행을 조합하는 조회는 별도의 네트워크 저장소 계약에 둔다.
- 사용자 설정 수정, 잠금 조회, 점수 일괄 갱신, 멤버십 삭제처럼 실행 조건과 보장이 다른 커맨드는 호출부에서 식별할 수 있어야 한다. 아카이브 포트는 관계 아카이브 후보를 받고 JPA 엔티티 변환은 어댑터가 맡는다.
- 이미 친구인 쌍의 관계 생성은 `AlreadyFriendsException`으로 처리한다. 복합 기본 키가 중복 관계를 막으며, 중복으로 실패한 수락에서는 요청 삭제와 수락 이벤트 발행을 진행하지 않는다.
- 친구 요청의 중복 범위는 순서 없는 사용자 쌍이다. 중복 확인은 그 쌍을 기준으로 하고, 요청의 권한과 조회에 필요한 발신자·수신자 방향은 보존한다.
- 내부 관계·요청 식별은 두 사용자 ID를 값으로 전달한다. 기존 응답의 문자열 ID 형식은 API 경계에서 유지한다. 친구·요청 조회의 활성 계정 조건과 표시 정보 조립은 역할을 분명히 하고, 한 응답을 만들 때 같은 프로필을 반복 조회하는 경로를 정리한다.

## Acceptance Criteria

- Social의 애플리케이션 서비스 이름이 위 책임을 반영하고, 이관 때 생긴 중복 서비스와 저장소 계약이 정리된다. Buzz와 Flag는 Social의 공개 계약을 통해 필요한 정보에 접근한다.
- 친구 관계 행을 다루는 저장소와 네트워크 조회 저장소가 각각의 계약으로 구분된다. 아카이브 포트의 시그니처와 변환 로직은 애플리케이션과 도메인을 JPA 엔티티에 의존시키지 않는다.
- 기존 친구·친구 요청·라벨·프로필·관계망 API의 경로, 입력, 응답, 권한·노출 규칙을 보존한다. 공통 친구 경로는 기존 2홉 조회 동작을 유지한다.
- 동일한 입력에서 Buzz 라벨 수신자는 발행자가 소유한 라벨의 활성 멤버 ID 집합으로 유지되고, 기준 친구 수신자 조회도 동일한 후보를 반환한다.
- 기존 관계의 사용자 설정이나 점수를 바꾸지 않고 중복 생성이 오류로 끝난다. 양방향 동시 요청은 최대 한 건만 남으며, 중복 관계로 수락이 실패하면 요청이 보존되고 수락 이벤트가 발행되지 않는다.
- 친구 요청 수락의 원자성, 한쪽 설정의 부분 갱신, 점수 갱신의 잠금 순서와 일괄 저장, 친구 끊기 및 아카이브의 양쪽 라벨 정리와 롤백이 회귀 테스트를 통과한다.
