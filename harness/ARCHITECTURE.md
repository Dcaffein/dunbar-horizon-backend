# Backend Architecture

백엔드는 기능별 모듈로 나뉜다. 각 모듈은 헥사고날 아키텍처(Ports & Adapters)에 따라 비즈니스 규칙을 `domain`, 유스케이스를 `application`, 외부와의 연결을 `adapter`에 둔다. 모듈마다 필요한 구성 요소만 둔다.

## Domain

비즈니스 개념과 규칙을 표현하는 계층이다. 도메인은 허용되는 상태와 상태 전이를 정의하고, 주어진 상태에서 불변식을 검증한다.

Social의 친구 요청과 친구 관계는 생성 규칙을 공유하므로 `domain.friendship`에 함께 둔다. 라벨 규칙은 `domain.label`, 관계망 조회 정책은 `domain.network`, 여러 기능이 공유하는 오류는 `domain.exception`에 둔다.

- **도메인 모델 (Domain Model)**은 엔티티, 값 객체, 애그리거트로 도메인의 상태와 행동을 표현한다. 각 모델은 자신이 책임지는 상태의 생성 조건과 변경 규칙을 판단한다. 그 판단에 관련 모델의 상태가 필요하면 읽기 용도로 참조할 수 있다. 이때 규칙을 맡은 모델이 상태를 제공하는 모델에 단방향으로 의존한다.
- **도메인 서비스 (Domain Service)**는 어느 한 모델의 책임에도 자연스럽게 속하지 않는 비즈니스 정책을 구현한다. 여러 애그리거트의 상태를 종합해 판단해야 하는 정책이 그 예다. 이름은 그 정책이 도메인에서 하는 일로 짓는다. `Service`, `Manager`, `Policy`처럼 무엇이든 담을 수 있는 일반 접미사는 쓰지 않는다.
- **도메인 예외 (`exception`)**는 모델의 상태나 비즈니스 규칙 때문에 연산을 완료할 수 없는 이유를 도메인 용어로 표현한다. HTTP 응답으로 변환하는 책임은 웹 계층에 있다.
- **도메인 이벤트 (Domain Event)**는 도메인에서 이미 일어난 일을 표현한다. 그 사실에 대한 후속 동작은 이벤트를 받는 쪽에서 처리한다.

## Application

유스케이스를 실행하는 계층이다. 필요한 사실을 조회하고 도메인 로직을 호출한 뒤 결과를 저장하거나 반환한다.

Social에서는 서비스와 이벤트 리스너를 기능 패키지에 둔다. 해당 기능의 입출력 포트와 DTO는 각각 `port`, `dto` 하위 패키지에 둔다. 다른 모듈은 해당 기능의 입력 포트를 호출한다.

- **입력 포트 (`port/in`)**는 다른 모듈에 공개하는 유스케이스의 인터페이스다. 다른 모듈이 사용하는 메서드만 선언하고 애플리케이션 서비스가 구현한다. 같은 모듈의 컨트롤러, 리스너, 스케줄러는 서비스를 직접 호출한다.
- **출력 포트 (`port/out`)**는 유스케이스가 외부 API, 다른 모듈, 저장소에 요청하는 작업의 계약이다. 애그리거트를 불러오고 저장하는 저장소 계약도 출력 포트에 둔다. 도메인은 판단에 필요한 사실을 인자로 받으므로 저장소에 의존하지 않는다. 유스케이스 전용 조회는 조회 조건과 반환 형태를 출력 포트에 정의한다.
- **애플리케이션 서비스 (`service`)**는 유스케이스를 구현한다. 트랜잭션 경계를 정하고 조회, 도메인 모델과 서비스 호출, 저장, 후속 작업의 순서를 조율한다. 동시 쓰기를 직렬화해야 하면 포트를 통해 필요한 잠금을 획득하고, 도메인에는 판단에 필요한 상태를 전달한다. 쓰기 유스케이스는 판단에 필요한 다른 모듈의 사실을 출력 포트로 확인한 뒤 도메인 로직을 호출한다. 틀린 판단이 상태로 남지 않도록 규칙의 주인에게 묻기 위해서다. 조회 유스케이스는 결과 형태에 맞춘 쿼리로 데이터를 받고, 다른 모듈의 규칙이나 도메인 규칙이 필요한 판정만 포트와 도메인 모델에 맡긴다. 이 구분이 맞지 않는 경우를 발견하면 다르게 구현하기 전에 사용자에게 알린다.
- **이벤트 리스너 (`eventListener`)**는 이벤트를 받아 후속 유스케이스를 시작한다.
- **DTO (`dto`)**는 유스케이스의 입력과 결과를 담는 데이터다. 하위 패키지로 나눌 때는 입력을 `command`, 결과를 `result`에 둔다.

## Adapter

애플리케이션을 HTTP, 스케줄러, 저장소, 외부 시스템과 연결하는 계층이다.

- **입력 어댑터 (`adapter/in`)**는 외부 입력을 유스케이스 호출로 변환한다. `web`에는 컨트롤러와 HTTP 요청·응답 DTO를, `scheduler`에는 정해진 시점에 유스케이스를 실행하는 진입점을 둔다.
- **출력 어댑터 (`adapter/out`)**는 애플리케이션 출력 포트의 계약을 구현한다. 외부 시스템이나 다른 모듈을 호출하는 어댑터는 역할이나 대상 이름으로 구분한다. 다른 모듈의 기능을 사용하거나 쓰기 판단에 그 모듈의 비즈니스 규칙이 필요하면 공개된 입력 포트(`UseCase`)를 호출한다.
- **영속성 어댑터 (`adapter/out/persistence`)**는 계약을 충족하는 데 필요한 DB 연산을 조합하고, 실제 접근은 저장 기술의 접근 객체에 맡긴다. 조회 경로는 공유 DB에 저장된 다른 모듈의 참조 데이터를 SQL로 직접 조인할 수 있다. 거르기·정렬·페이지 자르기를 한 쿼리 안에서 정확히 하기 위해서다. 직접 조인에는 소유 모듈이 SQL 정의를 공개한 조건만 쓰고, 그 조건을 쿼리마다 다시 적지 않는다. 공개된 정의가 없는 판정은 포트를 거친다. 이 경계가 맞지 않는 경우를 발견하면 다르게 구현하기 전에 사용자에게 알린다. 불변식에 영향을 주는 모든 쓰기 경로에서 DB 제약, 조건부 갱신, 잠금으로 필요한 원자성을 보장한다. 유일성은 DB 제약으로 보장하고, 해당 제약 위반은 도메인 예외로 바꾼다. 쿼리로 직접 갱신·삭제하면 영향받은 행 수를 확인해 기대한 결과가 조용히 빠지지 않게 한다. 기대와 어긋나면 예외나 결과값으로 호출자에게 알린다. 한 행을 여러 주체가 쓰면 각 주체는 자기 몫의 열만 갱신한다. 관계형 DB에서는 연산의 성격에 따라 JPA Repository나 JdbcTemplate을 사용한다.
    - **JPA**는 애그리거트를 불러와 도메인 모델의 행동으로 상태를 변경하고, 그 변경을 영속성 컨텍스트로 관리하는 쓰기 경로에 사용한다.
    - **JDBC**는 영속성 컨텍스트 없이 SQL로 직접 처리하는 조회와 대량 갱신에 사용한다.

소스 코드의 의존성은 `adapter`에서 `application` 또는 `domain`으로, `application`에서 `domain`으로 향한다. 서비스가 외부 기능을 사용하면 서비스는 인터페이스를 참조하고 어댑터가 그 인터페이스를 구현한다.
